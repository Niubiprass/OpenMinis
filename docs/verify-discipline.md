# 判据纪律(ios15_verify)

> 这份文档记录的是**流程纪律**, 不是某一条判据。
> 判据代码在 `scripts/ios15_verify/`, 注入在 `scripts/ios15_fallback.py`,
> CI 关卡在 `.github/workflows/port-and-build.yml`(断言 38~52)。
>
> 下面每一条都对应一次**真实**的 CI 失败(run#117~#120)或本地漏放,
> 不是预防性想象。

## 0. 为什么写这份文档

v49 那一版连续四次 CI 红, 四次的根因**没有一次是判据逻辑错**:
一次是判据区间边界算宽了、一次是脚本硬编码本地路径、两次是
**编译器级 API 错误而结构判据全程放行**。

也就是说: 判据能证明"我写的代码符合我写检查的那些形状",
但证明不了"我写的代码能编译"、也证明不了"我没把上一版的保护弄坏"。

纪律就是逐个补上这些缺口。

## 1. 每一版都要重跑全部历史判据

`regress_all_v.py`(CI 断言 52)在**同一份产物**上重跑 v41~v49 的所有判据
+ v47/v48 反向 + v49 的 sabotage。

**为什么**: run#117 里 v49 自己的四层判据全绿, 绿的是它自己,
红的是**v48 的判据** —— v49 探针插进了 v48 判据的区间里, 把三行
记忆位写入算进了 v48 的写入白名单。

> 只跑本版判据看不见"本版把历史保护弄坏"。
> 这是结构性的, 不是偶发, 所以必须做成 CI 关卡而不是靠记得手跑。

## 2. 顺序纪律: 先计数锁死集合, 再用 `find()` 取位置

**反例(run#118)**: v47 判据先用 `find()` 抓前两个 `// [V47-REWRAP]`
标记算段边界, 最后才检查标记数是否恰好 2。
反向测试 C3 往文件里塞了第三个标记 ⇒ 被抓到的"第二个"变成了那个多出来的
⇒ 段切片横跨 v48 的钉宽写入 ⇒ 报出一条与 sabotage 意图完全无关的措辞。

> **凡是"先切段、后校验标记存在性"的判据, 顺序都是错的。**
> 因为切段用的位置本身就依赖标记的数量正确。

同一类错误在 v49 项目的 `verify_width_reflow_v47` 里也有一份,
两处必须同时改。

## 3. 白名单只验名字, 不验接收者

**反例(run#119)**: E 层的 `inherited` 白名单里有 `"bounds"`
(那是宿主类的 UIView 成员), 于是 `self.textContainer.bounds`
被当成"合法继承成员"放行 —— 但 `NSTextContainer` 根本没有 `bounds`
(那是 `NSView` 的 API)。

> **同一个名字挂在不同类型的链路上, 合法性完全不同。**
> 要按接收者类型建表(`KNOWN_MEMBERS`), 并沿链**逐跳**推进。

沿链逐跳的两个坑(写完立刻反向证伪才发现):

```
① 链正则只写两段链 ⇒ 看不到真正要查的那一跳 ⇒ sabotage 全漏放
② 遍历时"当前节点不在表里就 break", 而 chain[0] 恒为 "self"
   ⇒ 第一跳就 break ⇒ 后面每一跳都不检查 ⇒ E 层形同虚设
```

**纪律: 任何检查写完必须立刻用 sabotage 反向证伪一遍。**
不证伪的检查等于没写 —— 上面两个坑都是"看起来在跑、实际全漏"。

## 4. 判据/探针里只允许出现编译器已验证存在的 API

**反例(run#119 + run#120)**: 连续两次编译失败, 两次都是
"这个 API 到底存不存在":

| 写法 | 结果 |
|---|---|
| `textContainer.bounds.width` | `has no member 'bounds'` |
| `textContainer.lineFragmentWidth` | `has no member 'lineFragmentWidth'` |

两次都是**凭"听起来对"猜 API 名**。第一版甚至在注释里论证
`lineFragmentWidth` "比 bounds 更贴排版路径, 判读力不减" ——
论证得越自信, 错得越彻底, 因为它让自己相信了那个不存在的 API。

> **写注释不能代替查证。** 本机没有 swiftc, 无法编译验证,
> 所以更要用**上游已在用的写法**(同一份文件里 40+ 处在读
> `textContainer.size`)或**官方文档**, 而不是记忆。

这类错误结构判据查不出来(它只查名字合不合法), 所以要单独一层:

- `scope_check_v49.py` E 层: 按接收者类型查成员是否存在
- `verify_v49.py`: 对已知不存在的 API 硬禁
- `reverse_v49_scope.py` S7~S12: 6 条 sabotage 自证 E 层真会拦

## 5. 描述文案本身也是判据的一部分

**反例**: `scope_check_v49.py` 拦下 `textContainer.bounds` 时,
提示文案写的是"请用 lineFragmentWidth(排版行宽)" ——
而 run#120 正是**照上一版的这条建议**改的, 结果它同样不存在。

```swift
// 一个把下一个人推向编译错误的提示, 比没有提示更坏。
```

同理, 断言描述里的条数(`struct 70 条` / `sab 11 条`)在判据扩充后
没跟着改, 差一条就会让人以为某条判据不存在。

> **判据的输出文案会主动塑造后来人的修法。**
> 数字要**当场从判据输出里取**, 不许手写;
> 不知道语义的东西不要"顺手改" —— v41/v42 文案里的
> "5 条诊断 / 4 条诊断"指注入的日志条数而非判据条数, 本轮核实不了
> 含义, 就不动。

## 6. 判据自己必须能被证伪

`regress_all_v.py` 认三种退出码:

| 码 | 含义 |
|---|---|
| 0 | 真通过 |
| 1 | 真失败 |
| **3** | **无法检查(SKIP)** |

> SKIP 绝不能算通过。run#118 之前 `ci_assert_v49.py` 找不到 fallback 时
> `return 0`, 打出来的却是 `✅ v49 SKIP(...)` —— **假绿**。
> 判据没跑就等于没人看守, 比红更危险。

## 7. 环境相关的路径不许硬编码

`reverse_v47.py` 原本硬编码 `/tmp/v47run`(本地调试目录),
CI 上不存在 ⇒ run#118 整条反向测试挂掉。
`verify_v46.py` 里还有一段 `/workspace/OpenMinis` 死代码,
CI 上恒为 `None`, 且**赋值后从未使用**。

> 判据要能接受产物根目录参数, 候选顺序 = 参数 → 仓库工作区 → 历史路径。
> 硬编码的路径是"本地能跑、CI 必红"的固定雷。

## 8. workflow 的 `paths` 必须包含判据目录

原先只列了注入脚本, 于是**只改判据不改进注入时 CI 根本不触发** ——
而"判据被改坏/被删"恰恰是最需要 CI 发现的改动。

```yaml
paths:
  - "scripts/ios15_fallback.py"
  - "scripts/ios15_verify/**"   # ★判据目录必须也在
  - ".github/workflows/port-and-build.yml"
```

## 9. 同一份逻辑只能有一处实现

v48 判据的段右边界在**两处**都有副本(fallback 内的
`verify_width_pin_v48` + 独立 `ci_assert_v48.py`),
本轮之前已因"只改一份"栽过三次。

> 副本必然漂移。要么合并, 要么让一处从另一处派生。

## 10. 段右边界不许硬编码版本号

v48 判据的段右界改过两次, 两次都是同一个错误:

1. 原先用下游的 `// [IOS15-FIX-RELC v28]` 标记 → v49 探针插在中间, 误伤
2. 改成 "v49 探针起点" → **这仍是同一个错误的重演**(硬编码到具体版本)
3. v50 又把通道写入插在 V48-PIN 与 v49 探针之间 → 再次误伤

正确做法: 右界 = `V48-PIN` 之后**第一个版本号 > 48 的标记**, 用正则现场扫:

```python
_V48_END_RE = re.compile(r"//\s*\[V(?:49|[5-9]\d|\d{3,})[ \-\]]")
m = _V48_END_RE.search(t, i_pin + len(PIN))
```

这样 v49/v50/v51… 无论插在哪一处都会被自动切掉。

> 根因不是"锚点选错了", 是**锚点选法错了**: 每来一个新版本就得改一次
> 判据, 改一次就漏一次。凡"下次加版时记得同步"的设计, 一定会被忘。

## 11. 判据与产物冲突时, 先问「这条红线当初为了防什么」

跨代失败分两类, 修法相反:

| 类别 | 症状 | 修法 |
|---|---|---|
| **边界误伤** | 新代码落进旧判据区间, 而旧判据本身**仍然正确** | 改**边界** |
| **语义作废** | 旧判据断言的那个**形态本身**已被实测证明是病根 | 改**语义** |

v50-C 就是第二类: v47 的 `idem` 断言"回写与 `ensureLayout` 同块",
而那个形态**正是** v49 实测 `laidW=-1` 占 138/143 的成因 ——
继续保留它就是保留 bug。

> 防得住病根的红线才留; 防的恰好是病根的必须改。

## 12. 反向测试的锚点失效必须自己报错

`str.replace(old, new, 1)` 在 `old` 不存在时**静默返回原串**。
于是锚点一旦因上游改动而失效(比如缩进从 16 变 12), sabotage 变成 no-op ——
产物没被破坏, 判据自然全绿 ⇒ 输出"★漏放"。

而真相是"这条 sabotage 根本没构造出来"。两者输出都是"漏放", 修法完全相反:
前者要改判据, 后者要改锚点。

```python
def assert_replaced(src, old, new, name):
    if old not in src:
        raise SystemExit("★锚点失效: %s 的替换目标不在产物里" % name)
    out = src.replace(old, new, 1)
    if out == src:
        raise SystemExit("★锚点失效: %s 替换后产物未变" % name)
    return out
```

> 锚点缩进必须**从产物数出来**。v50 那次 16 → 12 就栽在这里。

## 13. 查数据流要连「声明」一起查

v50 的 R1 判据第一版只查"读通道那一行有没有 probe 条件"——
结果把 `let _v50IsProbe = ...` 整行删掉, R1 仍绿,
而产物**根本编译不过**(未声明标识符)。数据流是断的。

补的第二条:

```python
m_pre = re.search(r"let (?P<pre>_v50IsProbe)\s*=\s*"
                  r"lineFrag\.width\s*>=\s*(?P<pre_s>[\d_]+)", seg)
# ① 声明必须存在  ② 哨兵必须与下方原判定一致  ③ 声明必须早于使用
```

> 用**命名分组**而不是位置分组 —— 位置编号也是数出来的,
> 跟"判据里的计数必须从产物数出来"是同一条纪律。

## 14. 提交纪律: git data API 单次提交

用 Contents API 多次 PUT 会触发多个 CI run, 每次重跑 20 分钟。
`scripts` 里的 `/tmp/push_*.py` 走 git data API:
读 ref → 读 base tree → 逐文件建 blob → 建新 tree → **单个 commit** → 更新 ref。

## 15. ★ 判据自身的误报, 比没有判据更贵

v64 写判据时我加了一条正则, 检查"收敛闸有没有被写成无条件":

```python
# ✗ 这条对**正确的注入**也报错
if re.search(r"_ios15Reconciled\s*=\s*_v64est\s*\n\s*\}\s*\n\s*fittingSize", infra):
    raise RuntimeError("收敛闸看起来是无条件保留 est")
```

正则假设了闸门块与后续语句的**缩进关系**, 而实际注入的缩进与假设不符 ⇒
**基线被判红** ⇒ 判据自己把自己的正确产物判成坏的。

> 判据误报的危害不是"漏过一个 bug", 而是**让人开始不信判据**。
> 一旦判据报过假红, 后面它报真红时就会被忽略 —— 那一刻它就彻底失效了,
> 比从未写判据更糟(至少没写的时候你知道没有守卫)。

**两条纪律**：
1. 判据里**不要叠"看形状像 X"的正则**。要么直接查实质条件
   (`"_v64grew && !_v64tkFresh" not in gate`), 要么交给专门的 sabotage。
2. 判据必须**在基线上先跑一遍并通过**, 才允许拿去判别产物。
   基线不通过就说明判据自己坏了, 不是产物坏了。

## 16. ★ sabotage 必须自己证明"它真的破坏了什么"

v64 的 S8 第一版: 把收敛闸整块挪到 `lastComputedHeight` 写回点**之前**,
理由是"这样闸门就在写回之后了"。

但基线里闸门**本来就在写回之前** ⇒ 插到写回点之前 = 插到闸门和写回**之间**
⇒ **相对顺序根本没变** ⇒ 什么都没破坏。

判据此时"漏过"了一个**根本没被破坏**的形态, 输出与"判据失灵"完全一样,
但修法相反(要改 sabotage, 不是改判据)。

**修法**：
- sabotage 完成后**立刻检查 `t == base`**, 相等就是空测, 独立计数不计入通过
  (与 §12 的 `assert_replaced` 同源, 但更靠后: 替换"成功"不等于"破坏到位")
- 破坏"**顺序**"这类关系时, 必须先确认基线的顺序, 再插到**真的**另一侧

## 17. ★ 反向 sabotage 要覆盖"换个名字继续错"

v64 判据里原本逐字匹配 `attrs.size.height`。S5 把它改回去, 判据抓到了。

但如果有人(including 未来的我)把播种写成 `height: lastComputedHeight` ——
**同样是"取上一轮的结果"**, 逐字匹配会漏过。

⇒ S6 专门构造这一条, 强制判据按**语义**禁:
> 播种语句里不得出现**任何**来自上一轮结果的来源,
> 而不是「不得出现 `attrs.size.height` 这个字符串」。

**一般规律**: 判据禁"某种写法"时, 必须问一句
「换个变量名/换个 API 绕过去, 判据还拦得住吗?」

## 18. ★★ 判据必须查「引用的东西存不存在」

run#159: v64 全链本地 **35 通过 / 0 失败 / 0 跳过**、幂等 3 轮逐字节相同、
反向 9 条全拦 —— 然后编译红:

```
MessageListInfrastructure.swift:762:27: error: cannot find '_v64found' in scope
```

一个字符的错(`_v64found` vs `_ios15Found`)。**全文仅此一个错误**。

### 为什么每一条判据都漏了

它们全都只查**文本在不在**: 标记在不在、表达式在不在、数据流顺序对不对。
`_v64found` 确实出现在闸门代码里 ⇒ "条件在位"成立 ⇒ 全绿。

sabotage 也一样: 9 条全是「破坏已存在的东西」, **没有一条制造一个
「引用不存在的标识符」**。⇒ 这不是判据松, 是**判据的种类缺失**。

### 修法

```python
# ① 白名单式: 逐个核对外部标识符真有声明(let/var 才算, 纯引用不算)
for ident in ("_v64est", "_v64tk", "_ios15Reconciled", ...):
    if not re.search(r"\b(?:let|var)\s+%s\b" % re.escape(ident), infra):
        raise RuntimeError("引用的 %r 没有声明 —— 编译必报 cannot find in scope")

# ② ★反向式(更重要): 不依赖维护清单, 谁新写变量忘了 let 都会被抓
declared = set(re.findall(r"\b(?:let|var)\s+(_v64\w+)", gate))
unknown  = set(re.findall(r"\b(_v64\w+)", gate)) - declared
if unknown:
    raise RuntimeError("用了未声明的 %s" % sorted(unknown))
```

**② 才是关键**: 白名单会随新代码过时, 反向式自动覆盖任何新增。

### 并把真实错误固化成 sabotage

```python
def s10_bad_identifier(t):
    """收敛闸引用不存在的标识符 —— run#159 的真实错误。"""
    return t.replace("let _v64tkFresh = _ios15Found && ...",
                     "let _v64tkFresh = _v64found && ...", 1)
```

> 这次浪费的是**一整次 CI run**, 不是时间。
> 而且它揭示了系统性盲区: **任何靠正则检查文本的判据, 都查不出「引用未定义」**。

### 四次「判据全绿」的一条共同规律

| 次数 | 缺的那一类 |
|---|---|
| run#156 | 判据**自己跑没跑** |
| run#157 | **语法合法性** |
| v64 初版 | **行为实质**(标记在位 ≠ 药有效) |
| run#159 | **引用完整性** |

⇒ 判据只查「我写下的东西在不在」, 从不查「它引用的、依赖的、声称成立的,
实际是不是真的」。**每加一层判据, 问的都是同一个问题。**

### 附: 验证修复必须从干净上游重建

```python
if "[V64-DESEED]" in t:
    return t          # ★幂等短路
```

修完注入代码后直接对**旧产物**重跑 ⇒ 短路生效 ⇒ 产物里**仍是错的**,
而所有判据都会绿(它们看到的是一个自洽的旧版本)。

⇒ 改注入代码后, 验证前必须 `rm -rf` 产物树并从干净上游重建三阶段。
这与纪律第 1 条是同一条, 只是这次踩得更深: 连"我改了脚本"这件事本身
都被幂等挡住了。

## §19 标识符存在 ≠ 标识符**可见**（run#157 / #159 / v65 三次同族）

前两次只查「符号有没有被声明」，v65 补上了第三种形态：**声明了，但在别的作用域**。

| 版本 | 形态 | 编译器报什么 |
|---|---|---|
| run#157 | `static stored property` 在泛型类型里 | `static stored properties not supported in generic types` |
| run#159 | `_v64found` 从未声明 | `cannot find '_v64found' in scope` |
| **v65（本轮）** | `kProbeHeightCeiling` 声明在函数体内另一段 `{}` 的 `const` | `undeclared identifier` / `'x' is not declared in this scope` |

⇒ **判据第 ⑤ 层要同时查存在性与可见性。** 最省事的做法是**别引用**：

## §20 判据自己踩的三个坑（写判据时先看这段）

v65 写判据时**自己误报了三次**，全部因为「朴素地按文本匹配」：

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| ① | 标记在**注释**里 | 正则撞上注释里写的条件表达式，取到错的位置 | `_strip_comments`：注释替换成**等长空格**，偏移一一对应 |
| ② | 条件在 `if (...)` 的**括号**里，不在花括号块内 | 按花括号配平取块只能取到 body，看不到条件 | 单独验条件本身，再取它后面的 `{` |
| ③ | 合法代码里也有 `return` | 风暴熔断的 SKIP 分支里 `return` 是**对的**（丢哨兵正是熔断本意），一棍子打尽会误伤 | 只查修正块**内部**；块外的 return 归第③层管 |

★**共同形状**：判据用「文本形状」去代理「语义」，而文本形状 ≠ 语义。
每次写判据都要问一句：**这段文本里有没有"看起来该拦、实际合法"的东西？**

## §21 反向 sabotage 自己也可能设计错

v65 的 S2 最初写成「把 `return` 插在修正块**之外**、熔断逻辑之前」。
它**确实**破坏了「改完要转发」这个不变量，但判据为了不误伤风暴 SKIP 的合法 `return`
只查块内 ⇒ **漏过**。

发现后没有放宽判据去迁就 sabotage，而是**把 sabotage 改成插在块内** ——
语义完全等价（TextKit 同样收不到修正值），且无歧义。

⇒ 纪律：sabotage 被漏过时，**先问 sabotage 破坏的语义与判据声称的是否一致**。
不一致时改 sabotage，不要放宽判据 —— 放宽判据等于给假绿开门。

## §22 工具也会坏，而它的坏法会**伪装成判据报红**（CI#161）

CI#161（run 37271671515）红了一项，判据本身在同一次运行里是**绿的**：

```
❌ script ios15_verify/verify_guard_v65.py
     ❌ [Errno 2] No such file or directory: '"$GUARD_V65"'
```

真因不在判据，在**抽取器** `local_all_gates.py`：它用正则从 workflow 里抽判据调用
的参数，抽到的是**字面量** `'"$GUARD_V65"'`（带双引号的 shell 变量引用），
然后原样 `open()` 那个字符串。

| 层次 | 实际状态 |
|---|---|
| `verify_guard_v65.py` 判据逻辑 | ✅ 绿（全版本回归 37/0/0，v65 两项都在内） |
| `NSTextContainerSetSizeGuard.m` 里的 v65 补丁 | ✅ 绿（clang 语法检查 0 error） |
| `local_all_gates.py` 的**参数抽取** | ❌ 没做 shell 变量求值 |

### 22.1 为什么这类错最贵

`[Errno 2] No such file or directory` 出现在一条 `❌ script ...` 底下，
任何人看到都会本能地认定「**这条判据坏了**」，于是去读判据的逻辑、想判据哪里写错。
判据完全没问题。**排错方向被这条错直接带偏**，这就是它贵的地方 ——
比红本身贵，因为红至少指向了真问题。

⇒ 纪律：工具类失败必须让**报错形态本身就说明是谁坏了**。
本项目的做法是让抽取器在求不出值时抛
`抽取故障: … 的参数 '"$VAR"' 引用了 shell 变量 $VAR, 但整份 workflow 里找不到它的赋值。`
并由 `main()` 记成带 `EXTRACT-FAIL` 前缀的独立红项，与「判据报红」区分开。

### 22.2 「判据全绿」这个前提本身需要看守

既然工具坏着的时候所有判据都会以看不出真因的形态报错，
那么**工具必须自己也有反向测试**，否则「全绿」会在某个版本悄悄失去意义。
本项目为此新增 `reverse_local_all_gates.py`（9 条 sabotage），
并在 workflow 里单列为**断言 70** —— 它不进 `CHECKS` 也不进 `MANDATORY` 是不够的，
因为门禁自己坏了的话，`regress_all_v.py` 也一样报不出来。

### 22.3 抽取器的两个同族缺陷

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| ① | shell 变量未求值 | `'"$VAR"'` 被当文件名递下去 | 收整份 workflow 的 `VAR=value`，**先求值再传**；求不出就**显式报红** |
| ② | 管道/重定向吞进参数 | `python3 x.py . 2>&1 \| tee f` 的 `2>&1 \| tee f` 也被当参数 | 按 **token** 判，token 含 `\| & ; < > ( ) \` 或**纯数字**（FD）即截断 |

★ ② 的修法踩了一次：先按**字符**截（`[^\n\\|;&<>()]+`），结果 `2>&1` 的
`2` 留了下来变成参数 `['.', '2']`。**FD 是个独立的 token**，
必须单独判 `^\d+$`。⇒ 凡是要在 shell 文本里做结构切分，
**先决定按字符还是按 token，再写正则** —— 两者的边界不一样。

### 22.4 写反向测试时，**观测面必须真的在被改的那条路径上**

这条是 §21 的加强版，本轮在这条上错了**三次**：

| # | 错法 | 现象 | 修法 |
|---|---|---|---|
| ① | `monkeypatch G.ROOT` + 采集函数里硬引用 `G.collect_scripts()` | 9 条 sabotage 全部「结果完全没变」 | 采集函数**显式接收模块对象**；monkeypatch 只能影响「谁被调用」，影响不了「被调用的是哪个模块」 |
| ② | `exec` 出来的 `dict` 当模块用 | 8 条「拦下」全是同一个无关崩溃 `'dict' object has no attribute 'ROOT'` —— **假绿** | `types.ModuleType` 包一层再 exec |
| ③ | 观测点够不着被改的能力 | S6/S8/S9 三条真漏过 | 见下 |

★ ② 最危险：崩溃确实「暴露了故障」，但它崩的地方跟被改的那处能力毫无关系，
于是报出「8 拦下 0 漏过」的**漂亮假绿**。**比漏过更坏** ——
漏过至少知道自己没测到，假绿让人以为有人看守。

★ ③ 三条漏过逐条查下去，**全都不是判据宽，是观测面够不着**：

- **S6**（纯数字 FD 截断）：`2>&1` 是**一个** token（含 `&`），第一个条件就拦下了，
  纯数字分支在原 WF 里永远不生效 ⇒ 得单独放一个裸 `3` 当 FD。
- **S8**（剥引号不得过度）：观测点一开始写成 `"ss"`，正确版与过度版**都**剥成 `ss`
  —— 因为剥引号**只做一次**，两版结果相同，观测不到差别。
  过度剥引号的危害只发生在「**没有引号**但首尾相同」的 token 上（如 `a/b/c/a`）。
- **S9**（抽取故障必须记红）：改的是 `main()` 里的 `checks.append`，
  而反向只跑 `collect_scripts()` ⇒ **观测面根本不在同一条路径上**，
  怎么改都不会被发现。改为把 `main()` 源码也纳入观测面做静态判定。

⇒ 纪律：**sabotage 漏过时，先证明观测面真的在被改的那条路径上**，
再怀疑判据。顺序反了就会去放宽一个本来正确的判据（§21 的教训在工具层的重演）。

## §23 桩比真实 SDK 宽松 = 假绿（本项目第六次「验证手段骗了自己」）

CI#162（run 37275980272）编译红：

```
NSTextContainerSetSizeGuard.m:153:51: error: no member named 'width' in 'struct CGRect'
  153 |   _w = [UIScreen mainScreen].bounds.width - 32.0;
```

而 v65 推送前我做过**真实的 clang 语法+类型检查**（自建 UIKit/Foundation/objc 桩），
结果是 **0 error**。它没有骗我 —— 是**我的桩在骗我**。

### 23.1 根因：一行桩代码

```c
// 我写的桩：
typedef struct CGRect { CGPoint origin; CGSize size; CGFloat width; CGFloat height; } CGRectRec;
                                                                  ^^^^^^^^^^^^^^^^^^^^^^ 我加的
```

真实 SDK 里 `CGRect` **没有** `width`/`height` 字段 —— 它们是 CoreGraphics
`CGGeometry` 这个 **category** 提供的。而 **UIKit 的模块化导入不 re-export
该 category**，所以即使文件顶部有 `#import <UIKit/UIKit.h>`，
`bounds.width` 依然报 "no member named 'width' in 'struct CGRect'"。

我为了"让桩好写"给 `CGRect` 补了这两个字段，于是**桩比真实 SDK 宽松**，
编译检查就成了一盏永远绿的灯。

### 23.2 纪律

⇒ **桩只允许比真实 SDK 严格，不允许更宽松。**
给桩**加一个真实 SDK 没有的能力**（字段/方法/category/宏）＝ 帮被测代码
通过它本该过不了的检查。**桩多给的那一分宽容，会变成假绿。**

⇒ 判据：**先证明桩能抓到已知的坏形态**，再用它判被测代码。
本轮的验证顺序是：
1. 用**旧（已知坏）**代码跑严格桩 ⇒ 恰好复现 CI 那一行报错（证明桩真的严了）；
2. 再用**新**代码跑 ⇒ 0 error（这才算数）。

跳过第 1 步的话，"0 error" 只说明"桩没意见"，不说明代码对 ——
这正是 v65 那一轮栽的地方。

⇒ 写桩时若为了省事给某个类型加了成员，必须在桩里**写明为什么真实 SDK 也有**
（例：`CGSize` 的 `width/height` 是**真** struct 成员，
`CGRect` 的则不是 —— 两者只有一字之差，恰恰是本轮踩的那个坑）。

### 23.3 修法：能不依赖 category 就不依赖

`[UIScreen mainScreen].bounds.width` 改成 KVC：

```objc
NSValue *_bv = [[UIScreen mainScreen] valueForKey:@"bounds"];
if (_bv) _w = (CGFloat)[_bv CGSizeValue].width;
```

与同段已有的 `[... valueForKey:@"size"]` 风格一致，**纯运行期查找**，
不需要编译器认识任何 category 声明。兜底宽度从屏宽推 `358.0 - 32.0`
（日志实测的真实排版宽度，v13/v34 已实证不能用 390 满宽）。

★ 顺手扫了全文件的 category 依赖：除这行外，`origin/size/minX/midX/...`
**一处都没有**（真代码只用 `CGSize` 的真 struct 成员），所以这是**唯一**一处。

## §24 「替系统干活」的补丁越堆越厚 —— 先问"这机制在目标系统上存在吗"（CI#163 后）

v13–v65 修了六代。v65 收敛时回头看，发现**所有版本都在最底层
（`NSTextContainer.setSize:`）加判据**，而病根在上游：

> `UITableView.selfSizingInvalidation`（cell 内容变化**自动** resize + 多次失效
> **自动合并**成一次最优更新）是 **iOS 16.0+** 才有的 API。
> **iOS 15.5 上不存在。**

⇒ App 在 iOS 16 上开发/测试时高度是对的（系统帮它 resize、帮它合并），
换到 15.5 就抖 —— **不是 bug，是缺失的系统机制**。
而 `setSize:` 层的尺寸钳制**补不了这个缺**：缺的是"自动失效"和"合并更新"两个概念，
不是"尺寸太大"。⇒ 补丁越厚，离根越远。

### 纪律

**在给某个 OS 版本打补丁前，先确认那个版本"原生具备"该机制。**
查官方文档的**平台标注**（`iOS 16.0+` 这种），而不是"新系统里有这功能"的印象。
判据：若目标系统缺少该机制 ⇒ 补丁是在**替系统实现**，必须评估"能不能在正确的层做"
（cell 层 vs 文本层），而不是继续在当前层加第 N 条。

### 同族：注入层禁用会触发不可逆降级的 API

TextKit 的坑：iOS 16+ 上访问 `UITextView.layoutManager` 会让一个正在用 TextKit 2 的
text view **永久降级**到 TextKit 1，Apple 头文件注释写明
*"After this happens, .textLayoutManager will return nil — and any TextKit 2 objects you
may have cached will cease functioning"*，且**不可逆**。

⇒ 当前注入层已验证 TK1 API **零使用**，把它**固化成判据**，
防止将来有人顺手加一行 `layoutManager.invalidateLayout(...)`（一个看起来完全无害的调用）。
**"看起来无害"正是它危险的原因。**

### 附：官方文档优先于论坛用户答案

调研中遇到一条论坛回答称 "Since iOS 15, UITextView is backed by TextKit 2 by default"，
与 WWDC22 原文矛盾。**不采信**，因为官方 API 平台标注是 `iOS 16.0+`
（iOS 15 上连显式选 TK2 的构造器 `UITextView(usingTextLayoutManager:)` 都不存在）。
⇒ 冲突时以**官方文档的平台标注**为准；论坛答案记进文档时**必须标注冲突与不采信的理由**。

## §25 判据问「这个东西会不会变坏」，病根是「它会不会生效」—— 问错问题，绿灯就是假的

**这是本项目第八次「验证手段骗了自己」，也是最危险的一次**，因为它同时骗过了
判据、反向 sabotage、以及「全量回归 38/0/0」的所有绿灯。

### 装机铁证（`minis-2026-10-06.log`，iOS 15.5）

```
[V65] FIXED-NONPOSITIVE size=0.0x0.0 -> 326.0x1.0 total=1970881
container=0x283da6f80   × 61584 条日志（每 32 次打 1 条）
⇒ 实际进入修正分支 197 万次 / 11 秒 / 全部集中在同一个容器
内存 35.5 → 54.3 → 250.6 → 563.0 → 1128.0 → 1474.6 MB（+1.4GB）
PID 28466 的最后一条日志是风暴中的 guard 日志，2 秒后 28473 全新进程 ⇒ SIGKILL

storm-breaker SKIP        0 次
NONPOSITIVE-STORM         0 次
NONPOSITIVE-HARDSTOP      0 次
```

**三道闸门一条都没开**，而代码里三道闸门都写着、判据全绿、13 条反向全拦下。

### 病根：累加语句是死代码

```objc
} else if (_v65orig_h <= 0.0 || _v65orig_w <= 0.0) {
    s->commitCount += 1;
    if (s->commitCount > kStormForwardLimit) {   // ← per-tick 门槛
        s->nonPositiveStreak += 1;              // ← 埋在里面，永不执行
    }
}
```

`commitCount` 由 `if (_newTick) { s->commitCount = 0; }` **每 tick 清零**；
而 `0x0` 是「每 tick 只喂一两次」的形态 ⇒ 永远到不了 40 ⇒ streak 永不增长
⇒ 跨 tick 硬闸门永不触发。

### 为什么判据全绿

第 ⑦ 层判据（v66 写的）问的是：

> `nonPositiveStreak` **会不会被清零**？（`if re.search(r"nonPositiveStreak\s*=\s*0", code)`）

这个问题有**恒真的答案**。而病根是另一个问题：

> 它**会不会被累加**？（答案恒假）

⇒ **判据用一个永远为真的检查，替代了一个决定生死的性质。**
这与 §23「桩比 SDK 宽松」同族，但更隐蔽：桩是**外部**骗你，这里是**问题本身**问错了。

### 判据纪律

**凡是有「门槛 / 条件 / 循环 / 嵌套」包裹的赋值或调用，
判据必须断言它「**不在包裹之内**」，而不是断言「包裹它的东西是安全的」。**

具体做法：**数花括号深度**，而不是读代码「像不像生效了」。

```python
pre = seg[:acc.start()]
depth = pre.count("{") - pre.count("}")
if depth > 0:
    raise RuntimeError("累加位于嵌套 if 内 ⇒ 死代码")
```

这条判据在 v66 产物上实测报出**深度 +2**，与源码形态逐字吻合。

### 同一轮的第二个病：修正值是「活锁的燃料」

v66 的下界钳制**确实生效了**（日志实测 `0.0 → 1.0`），但：

```
197 万次修正的结果全是同一个值 1.0
⇒ 上游收到 1.0 与收到 0.0 是同一件事（1pt 装不下任何一行，排版回报 0 行）
⇒ 上游继续算崩 ⇒ 自反馈回路一秒都没被断掉
```

⇒ **修「空操作」（v65）不等于修「活锁」（v66）**：

| 病 | 症状 | 断的位置 |
|---|---|---|
| 空操作 | 修正成和原来**一样的值** | 改「**修正成什么**」 |
| 活锁 | 修正成上游**仍然不满意**的值 | 改「**还转不转发**」 |

### 附：闸门也不能太狠 —— 「停得彻底」不等于「活得下来」

v66 的硬闸门是 `if (streak > 400) return;`（**永久**停止转发）。它确实能止住内存，
但一旦触发，该容器**再也收不到任何 setSize** ⇒ 高度永久冻结 ⇒ 屏幕保留一整块旧几何
⇒ **巨大空白**——正是 v61 刚修掉的症状换个形态回来。

⇒ 守卫的唯一职责是**让 App 活下去**。永久冻结把内存问题原地换成了空白问题，
还顺手删掉了「上游万一自愈」的可能性。**这是让 App 死得更快。**

⇒ 改为**降频放行**（每 64 次放 1 次）：197 万 → 约 3 万次（1.4GB → 20MB 量级），
且保留上行通道。

### 同族判据：「字段存在」≠「有人写它」（§19 的新变体）

v68 引入 `lastGoodHeight` 字段。若只断言「字段在 GuardState 里」，
那么一个**从未被赋值**的字段也能全绿 —— 而非正高度的修正值正依赖它。

⇒ `assert_v68_streak_reachable.py` 第 ⑥ 条同时断言：
`lastGoodHeight` **既被读取也被赋值**（`s->lastGoodHeight = newSize.height` 必须存在）。

### 附一：判据自己也会错 —— 本轮当场抓住的三个（§15 的续）

写完 v68 判据后第一次跑，**它自己报错了**，而且报的是**假红**：

```
❌ ⑧ streak 累加在嵌套 if 内(深度 +1) —— v66 死代码原样
```

去产物里一看，代码是**对的**：`s->nonPositiveStreak += 1;` 明明与 `commitCount`
那段平级。根因在判据的深度算法：

```python
pre = seg[:acc.start()]
depth = pre.count("{") - pre.count("}")   # ❌ 裸差值
```

`seg` 是从 else-if 的 `{` 起的，所以 **`seg[0]` 那个 `{` 就是块自身**，深度基准是 1；
而问的是"是否还在**嵌套** if 内"，判据应是 `depth - 1`。

⇒ 三处判据（`verify_guard_v65` / `assert_v68_streak_reachable` /
`guard_scope_check`）全部改成**逐字符维护深度**并显式减去块自身那层：

```python
def _rel_depth(seg, upto):
    d = 0
    for ch in seg[:upto]:
        if ch == "{": d += 1
        elif ch == "}": d -= 1
    return d - 1          # 减掉块自身那层
```

★ 不用裸 `count` 差值：它对"已闭合的兄弟块"也恰好给出正确结果，**纯属巧合**；
一旦上游出现带 `}` 的字符串字面量或宏，立刻跑偏。**逐字符维护才是定义。**

⇒ 双向复验：新产物 depth=0（过），v66 旧产物 depth=1（精确报红）。

### 附二：锚点写死注释 = 判据静默失效（§17 第四种形态）

`reverse_guard_v65.py` 的 S12 空测了 —— sabotage 自己找不到锚点。原因是锚点把
**注释文字**也写了进去：

```python
old = "  CGFloat _ah = fabs(newSize.height);\n"
      "  if (!(_ah > 1.0)) { _ah = 1.0; }      // 0 / -0 / 亚 1pt 一律抬到 1"
                                     ^^^^^^^^^^^^^^^^^^^^^^^^ 注释
```

v68 把这一行展开成多行（要读 `lastGoodHeight`），锚点失配。

⇒ **注释是最容易变的部分**。拿它当锚点等于把判据绑在注释上，上游随手改一句
注释，判据就静默失效 —— 而 CI 上它依然显示"通过"。

⇒ 修正为**只匹配代码骨架**的正则（注释一律用 `(?:[^\n]*\n)*?` 跳过）：

```python
pat = re.compile(
    r"[ \t]*CGFloat _ah = fabs\(newSize\.height\);\n"
    r"(?:[^\n]*\n)*?"                            # 注释与 _prev 取值
    r"[ \t]*if \(!\(_ah > 1\.0\)\) \{\n"
    r"(?:[^\n]*\n)*?"                            # 钳制体
    r"[ \t]*\}\n")
```

⇒ §17 清单追加第 4 条：**锚点不得包含注释**。§16 说的"空测必须独立计"救不了它 ——
空测会被报出来，但如果没人盯着反向的输出，它同样是一道假绿。

### 附三：反向漏过是判据的**信息**，不是噪音

第一轮 17 条跑出 **S17 漏过**（去掉 `lastGoodHeight` 的赋值，判据仍绿）。
这条漏过指出判据只查了两件事：

- 字段在 GuardState 里 ✅
- 下界钳制块里**读**了 `lastGoodHeight` ✅

但没查**有人写它吗**。一个永远为 0 的字段能满足上面两条，而修正值正依赖它的值
⇒ 每次都退回 1.0 ⇒ 活锁照旧。

⇒ 补第 ⑨-3 层：`s->lastGoodHeight = newSize.height` 必须存在。
⇒ 复跑：**17 拦下 / 0 漏过 / 0 空测**。

★ 这也是 §19 的新变体：**「标识符存在 ≠ 可见」⇒「字段存在 ≠ 被赋值」**。

## §26 判据必须验「交付物本身」，不能只验「交付物的原料」

> 前八次假绿都是**判据问错了问题**。这一次不是问错 —— 是**根本没问**。

### 装机铁证（CI run 37357375487, commit `e72f6b6`, v68）

那个 run **全绿**，每一步都过了：

### 为什么前八次都没抓到

前八次假绿的形状是「判据问错了问题」（问「会不会被清零」而不是「会不会被累加」）。
这一次是**判据根本没看最终产物**——所有判据都作用在 `src/ios/**.m` **源码**上，
而「装机包里到底有没有这段代码」这件事**从来没被问过**。

> 源码正确 + 编译成功 + 打包成功 ⇒ 三件事同时成立，
> **仍不能推出「修复进了二进制」**。

这两者之间隔着**编译器与链接器**。这不是某一步写错了，而是**结构性缺口**。

### 判据纪律

1. **grep 源码查的是「我有没有写这段代码」；验二进制查的是「链接器有没有把它放进 App」。** 两者不能互相替代，必须各有一层。
2. **二进制级判据必须带对照组。** 上例里 `storm-breaker` / `probe-height` / `REJECT-NAN-INF` 都在（v4/v38-C 那一代），而 v65/v68 不在 ⇒ 证明「查对了二进制」，不是「脚本读错了文件」。没有对照组，报红时无法区分这两种情况。
3. **位置必须在最后。** 断言 72 放在 dyld 体检之后、IPA 上传之前 —— 上传前的最后一道闸门。放前面就等于验的是还没打包的产物。
4. **对照组缺失时报红信息要能区分两种成因**，否则报错本身又变成一次「验证手段骗自己」。

### 附：第九次的通用形态

前八次的根因都是**判据与被验对象之间隔了一层没被跨越的语义**：

| 次 | 隔的那一层 |
|---|---|
| §19 | 标识符**存在** ≠ **可见**（块作用域） |
| §25 | **会被清零** ≠ **会被累加**（问错问题） |
| §26 | **源码里有** ≠ **二进制里有**（编译器+链接器） |

⇒ 每次发现「绿灯 + 装机仍坏」，先问一句：**判据问的那个属性，和真正决定症状的那个属性，是不是同一个？**
