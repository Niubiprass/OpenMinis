# 判据纪律(ios15_verify)

> 这份文档记录的是**流程纪律**, 不是某一条判据。
> 判据代码在 `scripts/ios15_verify/`, 注入在 `scripts/ios15_fallback.py`,
> CI 关卡在 `.github/workflows/port-and-build.yml`(断言 38~52)。
>
> 下面每一条都对应一次**真实**的 CI 失败(run#117~#120)或本地漏放,
> 不是预防性想象。

## 0. 为什么写这份文档

v49 那一版连续四次 CI 红, 四次的根因**没有一次是判据逻辑错**:
一次是判据区间边界算宽了、一次是脚本硬编码本地路径、两次是
**编译器级 API 错误而结构判据全程放行**。

也就是说: 判据能证明"我写的代码符合我写检查的那些形状",
但证明不了"我写的代码能编译"、也证明不了"我没把上一版的保护弄坏"。

纪律就是逐个补上这些缺口。

## 1. 每一版都要重跑全部历史判据

`regress_all_v.py`(CI 断言 52)在**同一份产物**上重跑 v41~v49 的所有判据
+ v47/v48 反向 + v49 的 sabotage。

**为什么**: run#117 里 v49 自己的四层判据全绿, 绿的是它自己,
红的是**v48 的判据** —— v49 探针插进了 v48 判据的区间里, 把三行
记忆位写入算进了 v48 的写入白名单。

> 只跑本版判据看不见"本版把历史保护弄坏"。
> 这是结构性的, 不是偶发, 所以必须做成 CI 关卡而不是靠记得手跑。

## 2. 顺序纪律: 先计数锁死集合, 再用 `find()` 取位置

**反例(run#118)**: v47 判据先用 `find()` 抓前两个 `// [V47-REWRAP]`
标记算段边界, 最后才检查标记数是否恰好 2。
反向测试 C3 往文件里塞了第三个标记 ⇒ 被抓到的"第二个"变成了那个多出来的
⇒ 段切片横跨 v48 的钉宽写入 ⇒ 报出一条与 sabotage 意图完全无关的措辞。

> **凡是"先切段、后校验标记存在性"的判据, 顺序都是错的。**
> 因为切段用的位置本身就依赖标记的数量正确。

同一类错误在 v49 项目的 `verify_width_reflow_v47` 里也有一份,
两处必须同时改。

## 3. 白名单只验名字, 不验接收者

**反例(run#119)**: E 层的 `inherited` 白名单里有 `"bounds"`
(那是宿主类的 UIView 成员), 于是 `self.textContainer.bounds`
被当成"合法继承成员"放行 —— 但 `NSTextContainer` 根本没有 `bounds`
(那是 `NSView` 的 API)。

> **同一个名字挂在不同类型的链路上, 合法性完全不同。**
> 要按接收者类型建表(`KNOWN_MEMBERS`), 并沿链**逐跳**推进。

沿链逐跳的两个坑(写完立刻反向证伪才发现):

```
① 链正则只写两段链 ⇒ 看不到真正要查的那一跳 ⇒ sabotage 全漏放
② 遍历时"当前节点不在表里就 break", 而 chain[0] 恒为 "self"
   ⇒ 第一跳就 break ⇒ 后面每一跳都不检查 ⇒ E 层形同虚设
```

**纪律: 任何检查写完必须立刻用 sabotage 反向证伪一遍。**
不证伪的检查等于没写 —— 上面两个坑都是"看起来在跑、实际全漏"。

## 4. 判据/探针里只允许出现编译器已验证存在的 API

**反例(run#119 + run#120)**: 连续两次编译失败, 两次都是
"这个 API 到底存不存在":

| 写法 | 结果 |
|---|---|
| `textContainer.bounds.width` | `has no member 'bounds'` |
| `textContainer.lineFragmentWidth` | `has no member 'lineFragmentWidth'` |

两次都是**凭"听起来对"猜 API 名**。第一版甚至在注释里论证
`lineFragmentWidth` "比 bounds 更贴排版路径, 判读力不减" ——
论证得越自信, 错得越彻底, 因为它让自己相信了那个不存在的 API。

> **写注释不能代替查证。** 本机没有 swiftc, 无法编译验证,
> 所以更要用**上游已在用的写法**(同一份文件里 40+ 处在读
> `textContainer.size`)或**官方文档**, 而不是记忆。

这类错误结构判据查不出来(它只查名字合不合法), 所以要单独一层:

- `scope_check_v49.py` E 层: 按接收者类型查成员是否存在
- `verify_v49.py`: 对已知不存在的 API 硬禁
- `reverse_v49_scope.py` S7~S12: 6 条 sabotage 自证 E 层真会拦

## 5. 描述文案本身也是判据的一部分

**反例**: `scope_check_v49.py` 拦下 `textContainer.bounds` 时,
提示文案写的是"请用 lineFragmentWidth(排版行宽)" ——
而 run#120 正是**照上一版的这条建议**改的, 结果它同样不存在。

```swift
// 一个把下一个人推向编译错误的提示, 比没有提示更坏。
```

同理, 断言描述里的条数(`struct 70 条` / `sab 11 条`)在判据扩充后
没跟着改, 差一条就会让人以为某条判据不存在。

> **判据的输出文案会主动塑造后来人的修法。**
> 数字要**当场从判据输出里取**, 不许手写;
> 不知道语义的东西不要"顺手改" —— v41/v42 文案里的
> "5 条诊断 / 4 条诊断"指注入的日志条数而非判据条数, 本轮核实不了
> 含义, 就不动。

## 6. 判据自己必须能被证伪

`regress_all_v.py` 认三种退出码:

| 码 | 含义 |
|---|---|
| 0 | 真通过 |
| 1 | 真失败 |
| **3** | **无法检查(SKIP)** |

> SKIP 绝不能算通过。run#118 之前 `ci_assert_v49.py` 找不到 fallback 时
> `return 0`, 打出来的却是 `✅ v49 SKIP(...)` —— **假绿**。
> 判据没跑就等于没人看守, 比红更危险。

## 7. 环境相关的路径不许硬编码

`reverse_v47.py` 原本硬编码 `/tmp/v47run`(本地调试目录),
CI 上不存在 ⇒ run#118 整条反向测试挂掉。
`verify_v46.py` 里还有一段 `/workspace/OpenMinis` 死代码,
CI 上恒为 `None`, 且**赋值后从未使用**。

> 判据要能接受产物根目录参数, 候选顺序 = 参数 → 仓库工作区 → 历史路径。
> 硬编码的路径是"本地能跑、CI 必红"的固定雷。

## 8. workflow 的 `paths` 必须包含判据目录

原先只列了注入脚本, 于是**只改判据不改进注入时 CI 根本不触发** ——
而"判据被改坏/被删"恰恰是最需要 CI 发现的改动。

```yaml
paths:
  - "scripts/ios15_fallback.py"
  - "scripts/ios15_verify/**"   # ★判据目录必须也在
  - ".github/workflows/port-and-build.yml"
```

## 9. 同一份逻辑只能有一处实现

v48 判据的段右边界在**两处**都有副本(fallback 内的
`verify_width_pin_v48` + 独立 `ci_assert_v48.py`),
本轮之前已因"只改一份"栽过三次。

> 副本必然漂移。要么合并, 要么让一处从另一处派生。

## 10. 段右边界不许硬编码版本号

v48 判据的段右界改过两次, 两次都是同一个错误:

1. 原先用下游的 `// [IOS15-FIX-RELC v28]` 标记 → v49 探针插在中间, 误伤
2. 改成 "v49 探针起点" → **这仍是同一个错误的重演**(硬编码到具体版本)
3. v50 又把通道写入插在 V48-PIN 与 v49 探针之间 → 再次误伤

正确做法: 右界 = `V48-PIN` 之后**第一个版本号 > 48 的标记**, 用正则现场扫:

```python
_V48_END_RE = re.compile(r"//\s*\[V(?:49|[5-9]\d|\d{3,})[ \-\]]")
m = _V48_END_RE.search(t, i_pin + len(PIN))
```

这样 v49/v50/v51… 无论插在哪一处都会被自动切掉。

> 根因不是"锚点选错了", 是**锚点选法错了**: 每来一个新版本就得改一次
> 判据, 改一次就漏一次。凡"下次加版时记得同步"的设计, 一定会被忘。

## 11. 判据与产物冲突时, 先问「这条红线当初为了防什么」

跨代失败分两类, 修法相反:

| 类别 | 症状 | 修法 |
|---|---|---|
| **边界误伤** | 新代码落进旧判据区间, 而旧判据本身**仍然正确** | 改**边界** |
| **语义作废** | 旧判据断言的那个**形态本身**已被实测证明是病根 | 改**语义** |

v50-C 就是第二类: v47 的 `idem` 断言"回写与 `ensureLayout` 同块",
而那个形态**正是** v49 实测 `laidW=-1` 占 138/143 的成因 ——
继续保留它就是保留 bug。

> 防得住病根的红线才留; 防的恰好是病根的必须改。

## 12. 反向测试的锚点失效必须自己报错

`str.replace(old, new, 1)` 在 `old` 不存在时**静默返回原串**。
于是锚点一旦因上游改动而失效(比如缩进从 16 变 12), sabotage 变成 no-op ——
产物没被破坏, 判据自然全绿 ⇒ 输出"★漏放"。

而真相是"这条 sabotage 根本没构造出来"。两者输出都是"漏放", 修法完全相反:
前者要改判据, 后者要改锚点。

```python
def assert_replaced(src, old, new, name):
    if old not in src:
        raise SystemExit("★锚点失效: %s 的替换目标不在产物里" % name)
    out = src.replace(old, new, 1)
    if out == src:
        raise SystemExit("★锚点失效: %s 替换后产物未变" % name)
    return out
```

> 锚点缩进必须**从产物数出来**。v50 那次 16 → 12 就栽在这里。

## 13. 查数据流要连「声明」一起查

v50 的 R1 判据第一版只查"读通道那一行有没有 probe 条件"——
结果把 `let _v50IsProbe = ...` 整行删掉, R1 仍绿,
而产物**根本编译不过**(未声明标识符)。数据流是断的。

补的第二条:

```python
m_pre = re.search(r"let (?P<pre>_v50IsProbe)\s*=\s*"
                  r"lineFrag\.width\s*>=\s*(?P<pre_s>[\d_]+)", seg)
# ① 声明必须存在  ② 哨兵必须与下方原判定一致  ③ 声明必须早于使用
```

> 用**命名分组**而不是位置分组 —— 位置编号也是数出来的,
> 跟"判据里的计数必须从产物数出来"是同一条纪律。

## 14. 提交纪律: git data API 单次提交

用 Contents API 多次 PUT 会触发多个 CI run, 每次重跑 20 分钟。
`scripts` 里的 `/tmp/push_*.py` 走 git data API:
读 ref → 读 base tree → 逐文件建 blob → 建新 tree → **单个 commit** → 更新 ref。

## 15. ★ 判据自身的误报, 比没有判据更贵

v64 写判据时我加了一条正则, 检查"收敛闸有没有被写成无条件":

```python
# ✗ 这条对**正确的注入**也报错
if re.search(r"_ios15Reconciled\s*=\s*_v64est\s*\n\s*\}\s*\n\s*fittingSize", infra):
    raise RuntimeError("收敛闸看起来是无条件保留 est")
```

正则假设了闸门块与后续语句的**缩进关系**, 而实际注入的缩进与假设不符 ⇒
**基线被判红** ⇒ 判据自己把自己的正确产物判成坏的。

> 判据误报的危害不是"漏过一个 bug", 而是**让人开始不信判据**。
> 一旦判据报过假红, 后面它报真红时就会被忽略 —— 那一刻它就彻底失效了,
> 比从未写判据更糟(至少没写的时候你知道没有守卫)。

**两条纪律**：
1. 判据里**不要叠"看形状像 X"的正则**。要么直接查实质条件
   (`"_v64grew && !_v64tkFresh" not in gate`), 要么交给专门的 sabotage。
2. 判据必须**在基线上先跑一遍并通过**, 才允许拿去判别产物。
   基线不通过就说明判据自己坏了, 不是产物坏了。

## 16. ★ sabotage 必须自己证明"它真的破坏了什么"

v64 的 S8 第一版: 把收敛闸整块挪到 `lastComputedHeight` 写回点**之前**,
理由是"这样闸门就在写回之后了"。

但基线里闸门**本来就在写回之前** ⇒ 插到写回点之前 = 插到闸门和写回**之间**
⇒ **相对顺序根本没变** ⇒ 什么都没破坏。

判据此时"漏过"了一个**根本没被破坏**的形态, 输出与"判据失灵"完全一样,
但修法相反(要改 sabotage, 不是改判据)。

**修法**：
- sabotage 完成后**立刻检查 `t == base`**, 相等就是空测, 独立计数不计入通过
  (与 §12 的 `assert_replaced` 同源, 但更靠后: 替换"成功"不等于"破坏到位")
- 破坏"**顺序**"这类关系时, 必须先确认基线的顺序, 再插到**真的**另一侧

## 17. ★ 反向 sabotage 要覆盖"换个名字继续错"

v64 判据里原本逐字匹配 `attrs.size.height`。S5 把它改回去, 判据抓到了。

但如果有人(including 未来的我)把播种写成 `height: lastComputedHeight` ——
**同样是"取上一轮的结果"**, 逐字匹配会漏过。

⇒ S6 专门构造这一条, 强制判据按**语义**禁:
> 播种语句里不得出现**任何**来自上一轮结果的来源,
> 而不是「不得出现 `attrs.size.height` 这个字符串」。

**一般规律**: 判据禁"某种写法"时, 必须问一句
「换个变量名/换个 API 绕过去, 判据还拦得住吗?」

## 18. ★★ 判据必须查「引用的东西存不存在」

run#159: v64 全链本地 **35 通过 / 0 失败 / 0 跳过**、幂等 3 轮逐字节相同、
反向 9 条全拦 —— 然后编译红:

```
MessageListInfrastructure.swift:762:27: error: cannot find '_v64found' in scope
```

一个字符的错(`_v64found` vs `_ios15Found`)。**全文仅此一个错误**。

### 为什么每一条判据都漏了

它们全都只查**文本在不在**: 标记在不在、表达式在不在、数据流顺序对不对。
`_v64found` 确实出现在闸门代码里 ⇒ "条件在位"成立 ⇒ 全绿。

sabotage 也一样: 9 条全是「破坏已存在的东西」, **没有一条制造一个
「引用不存在的标识符」**。⇒ 这不是判据松, 是**判据的种类缺失**。

### 修法

```python
# ① 白名单式: 逐个核对外部标识符真有声明(let/var 才算, 纯引用不算)
for ident in ("_v64est", "_v64tk", "_ios15Reconciled", ...):
    if not re.search(r"\b(?:let|var)\s+%s\b" % re.escape(ident), infra):
        raise RuntimeError("引用的 %r 没有声明 —— 编译必报 cannot find in scope")

# ② ★反向式(更重要): 不依赖维护清单, 谁新写变量忘了 let 都会被抓
declared = set(re.findall(r"\b(?:let|var)\s+(_v64\w+)", gate))
unknown  = set(re.findall(r"\b(_v64\w+)", gate)) - declared
if unknown:
    raise RuntimeError("用了未声明的 %s" % sorted(unknown))
```

**② 才是关键**: 白名单会随新代码过时, 反向式自动覆盖任何新增。

### 并把真实错误固化成 sabotage

```python
def s10_bad_identifier(t):
    """收敛闸引用不存在的标识符 —— run#159 的真实错误。"""
    return t.replace("let _v64tkFresh = _ios15Found && ...",
                     "let _v64tkFresh = _v64found && ...", 1)
```

> 这次浪费的是**一整次 CI run**, 不是时间。
> 而且它揭示了系统性盲区: **任何靠正则检查文本的判据, 都查不出「引用未定义」**。

### 四次「判据全绿」的一条共同规律

| 次数 | 缺的那一类 |
|---|---|
| run#156 | 判据**自己跑没跑** |
| run#157 | **语法合法性** |
| v64 初版 | **行为实质**(标记在位 ≠ 药有效) |
| run#159 | **引用完整性** |

⇒ 判据只查「我写下的东西在不在」, 从不查「它引用的、依赖的、声称成立的,
实际是不是真的」。**每加一层判据, 问的都是同一个问题。**

### 附: 验证修复必须从干净上游重建

```python
if "[V64-DESEED]" in t:
    return t          # ★幂等短路
```

修完注入代码后直接对**旧产物**重跑 ⇒ 短路生效 ⇒ 产物里**仍是错的**,
而所有判据都会绿(它们看到的是一个自洽的旧版本)。

⇒ 改注入代码后, 验证前必须 `rm -rf` 产物树并从干净上游重建三阶段。
这与纪律第 1 条是同一条, 只是这次踩得更深: 连"我改了脚本"这件事本身
都被幂等挡住了。

## 附: 提交前本地自检

```bash
# 1) 从**干净上游**跑完整全链注入(不是从上一版产物叠加)
#    ★必须用干净上游: /tmp/pristine 那类"看起来干净"的树其实已被注入过
#    ★三阶段都要跑, 且要在**产物树内部**执行(见下方踩坑)
cd /tmp && rm -rf vXXfull && cp -a up-1.14 vXXfull
cp -a scripts/ios15_*.py vXXfull/scripts/          # 产物树要带自己的脚本
cd vXXfull && python3 scripts/ios15_port.py          # ①
python3 scripts/ios15_port_v2.py                     # ② 生成 iOS15Compat.swift
python3 scripts/ios15_fallback.py                    # ③ 注入 v21~v64

# 2) 跑全版本回归(目标 0 跳过)
python3 scripts/ios15_verify/regress_all_v.py /tmp/vXXfull

# 3) ★负向自检: 拿**只跑阶段①②**的产物跑判据, 必须报红
#    这是判据有分辨力的唯一证据。全绿说明判据在空测。
```

回归输出里 `0 跳过` 才是真通过 —— 有 SKIP 说明产物树不全。

> ⚠ **三阶段脚本用相对当前目录定位产物**(`TARGET_DIR = sys.argv[1] or "src/ios"`)。
> 在仓库根跑 `python3 scripts/ios15_port.py /tmp/x` 会**扫到仓库自己的 `src/`**
> 并就地注入。v64 期间踩过一次, 用 `git checkout -- src/` 还原。
> **正确姿势: `cd <产物树> && python3 scripts/ios15_port.py`**。
