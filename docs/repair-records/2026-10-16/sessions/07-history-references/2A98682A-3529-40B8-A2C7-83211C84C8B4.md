## 结论先行

适合移植的是**更新协议**，不是整库替换：

1. 一条流式消息始终使用同一个 messageID；内容版本和 cell 身份分离。不能把每次增长的全文/hash/临时 UUID 当作 cell ID。
2. **文字更新与高度失效必须分开**：同高度的新文字仍须显示；只有高度确实变化才通知列表布局。合并失效请求时保留最新内容和最后一次高度；可合并中间态，但最终新尺寸必须落地，也不依赖下一次 token 才冲刷尾部。
3. 先记录“锚点消息＋边缘＋距离”，更新后按新位置恢复。阅读历史时守住阅读位置；原本跟随底部时才继续跟随底部，不在每个 token 上强制 scrollToBottom。
4. 对输出中的文字，保留现有 cell、hosting controller、文本视图，原位更新；禁止为刷新而先清空文字、交替 alpha=0/1、换根视图身份。流式普通字不做淡入动画。
5. 输入的 markedText 是另一条路径：组合期间禁止模型回写覆盖 UITextView；提交时同步最终文本。InputBarAccessoryView **没有提供这一保护的源码证据**，不能声称引入它即可修复中文跳字。

## 1. ChatLayout：最值得借鉴的是身份、更新事务和位置补偿

### 两处主要源码

- **C1：稳定 ID 与重配置事务**：[ChatLayoutDiffableDataSource.swift L154–224](https://github.com/ekazaev/ChatLayout/blob/dd4cb5c8f91623331ba023d0ab64d844f8436204/ChatLayout/Classes/Core/ChatLayoutDiffableDataSource.swift#L154-L224)。同文件 L32–47 建立 ItemID→IndexPath 映射；L189–214 在 performBatchUpdates 内一并切换 snapshot 和业务模型；L194–201 对重配置保留旧 IndexPath→ID，避免插入/移动后旧索引指向另一条消息；L219–224 支持不动画更新。
- **C2：滚动锚点与布局控制**：[CollectionViewChatLayout.swift L270–353](https://github.com/ekazaev/ChatLayout/blob/dd4cb5c8f91623331ba023d0ab64d844f8436204/ChatLayout/Classes/Core/CollectionViewChatLayout.swift#L270-L353)。同文件 L521–537 为尺寸等布局属性变化判定，L540–614 为局部尺寸失效与 contentOffsetAdjustment，L638–688 为失效动作记录及快照恢复，L718–750 为重配置后显式测高。

### 已核实机制

**身份与内容分离。** 示例 `Example/ChatLayout/Chat/Model/Data Objects/Cell.swift` L17–49 中 ID 是 `.message(message.id)`，不是全文 Hashable 值；示例 `ChatViewController.swift` L592–625 对相同 ID 的内容变化区分 reconfigure/reload，同 cell 类型才优先 reconfigure。C1 强调 provider、布局 delegate 与 snapshot 必须在同一事务看见一致模型。

**显式尺寸更新，不依赖 iOS 16 自动 self-sizing。** C2 的 `supportSelfSizingInvalidation` 在 L85–99 明确 `@available(iOS 16.0, *)`，且称为 experimental，默认内部值 false。iOS 15 可参考的是 L718–750：重配置可见 cell，调用 preferredLayoutAttributesFitting，只在圆整后高度变化时做布局失效。L611–612 仅 invalidate 对应 item，避免不必要的全局 metrics 重算。L638–669 用 prepareActions 的集合并集记录待办，prepare L368–440 执行后清空；这是布局待办合并，**不是现成的 token 节流器**。

**位置 snapshot。** C2 获取靠近 top/bottom 的 item 与距该边缘的 offset；恢复时经 layout invalidation 补偿 contentOffset，并约束在有效滚动范围。注意库自带 `ChatLayoutPositionSnapshot` 保存的是 **IndexPath，而非业务 messageID**。如果插入、删除、移动了锚点前的消息，必须在业务层同时记录 messageID，更新后找到新 IndexPath；不能照搬旧 IndexPath。锚点消失时须定义邻近消息/底部回退。

### 适用与不适用

适用于 OpenMinis 现有 UICollectionView 的局部更新协议：保留 messageID，内容更新用 reconfigure 或现有可见 cell 的原位更新，并同步测高和滚动补偿。不能仅调用 UIKit reconfigure 而让自定义 layout 不知情；C1 L199–200 同时通知 collectionView 与 ChatLayout，正是这个问题的证据。

不适合直接复制：iOS 16 自动 self-sizing 开关、整套 ChatLayout 状态机、每 token 完整 snapshot/reload。C2 L346–350 也明确警告 reconfigure 对 layout 的通知存在限制、异常时考虑 reload；这不等于流式每 token reload，应在类型变更或确实无法原位更新时才用回退。`restoreContentOffset` 内部的两轮布局调用是库自己的状态机配套，不应移植成全局每帧强制 layoutIfNeeded。

## 2. InputBarAccessoryView：尺寸去重可借鉴，markedText 保护不能归功于它

### 两处主要源码

- **I1：文本变化只在必要时触发尺寸失效**：[InputBarAccessoryView.swift L874–907](https://github.com/nathantannar4/InputBarAccessoryView/blob/83cf29212e2cdb947226eead38a535c9b12629cb/Sources/InputBarAccessoryView.swift#L874-L907)。L893 比较 required height 与当前 bounds.height，L898–905 才通知尺寸失效，动画受单独开关控制。同文件 L237–247 的 intrinsicContentSize 返回缓存；L549–555 重算后只有与上次尺寸不同才通知 delegate；L284–289 用 sizeThatFits 测高。
- **I2：程序化赋值会发文本变化通知，但没有组合文本保护**：[InputTextView.swift L40–54](https://github.com/nathantannar4/InputBarAccessoryView/blob/83cf29212e2cdb947226eead38a535c9b12629cb/Sources/Views/InputTextView.swift#L40-L54)。text/attributedText 的 didSet 均调用 postTextViewDidChangeNotification，具体实现在同文件 L231–232。检索整个 Sources 的 markedText、unmarkText、setMarkedText 无命中；这是该 checkout 的限制，不是对 UIKit 行为的推测。

### 已核实机制与适用性

I1 很适合借鉴“**文字变了不等于高度变了**”：先处理文本变化，再按高度差决定是否让父布局更新；getter 返回缓存，避免多次查询 intrinsicContentSize 时重复测量。高度到达上限后才切换 UITextView 自身滚动（L562–579）。`shouldAnimateTextDidChangeLayout` 默认 false（L278–281），值得沿用给流式/输入常态，避免连续高度动画叠加。

但这只是**尺寸去重**，不是跨事件的请求合并；invalidateIntrinsicContentSize 内仍然立即重算。移植到 OpenMinis 时应在自己的协调层加 pending/scheduled 合并，不能把“库有缓存”说成“库已经解决 runloop 重入”。同样，重复发出 textDidChangeNotification 的做法不适合未经防回环设计的 SwiftUI binding 双向桥接：模型回写 text → didSet 通知 → delegate 更新模型，可能再次回写。

### markedText 的正确落地方向（建议，不是本库已有能力）

- UIViewRepresentable 的 updateUIView 回写前先判断 `textView.markedTextRange != nil`：组合期间不赋 text/attributedText，不重建 text view，不修改 selection，也不强制 unmarkText。等值文本也不重复赋值。
- 原生 UITextView 保有组合态和光标。确需展示实时草稿时可把当前内容发布给模型，但要区分“组合态草稿”与“最终提交态”，不能把此前草稿回灌覆盖正在输入的组合串。
- 在 textViewDidChange 等可靠回调中发现 markedText 已结束时，读取**当时 UITextView 的最终全文**一次同步；不能只屏蔽组合期回调却漏掉最后一次提交。外部清空/切换会话属于显式命令，按会话版本校验，不让旧异步赋值覆盖新会话。
- 输入高度仍可按实际当前文本测量并去重；markedText 保护不等于冻结整个输入框高度。是否在组合期间发送消息应有明确策略，不能先用过期 binding 发送再清空输入框。

不建议借用自动补全插件的全量 attributedText 重写作为流式输出策略；本库定位是输入 accessory，不解决聊天列表身份、输出气泡或滚动锚点。I2 也说明它不能作为“中文 IME 已有修复”的证据。

## 3. swift-markdown-ui：预解析思路有用，内容身份和 iOS 15 功能边界要避坑

### 两处主要源码

- **M1：模型层预解析与显示分离**：[Markdown.swift L60–71](https://github.com/gonzalezreal/swift-markdown-ui/blob/8371aeb32f35795a9e559029fb08613355733626/Sources/MarkdownUI/Views/Markdown.swift#L60-L71)。同文件 L206–225 接收 MarkdownContent 并渲染 blocks；L237–238 的 String 初始化器直接构建 MarkdownContent，因此每次重新用变化的 String 构建都可能重新解析，并非增量流式引擎。
- **M2：block 身份含内容，不是稳定消息/段落 ID**：[BlockSequence.swift L12–49](https://github.com/gonzalezreal/swift-markdown-ui/blob/8371aeb32f35795a9e559029fb08613355733626/Sources/MarkdownUI/Views/Blocks/BlockSequence.swift#L12-L49)。L27 是 `ForEach(self.data, id: \.self)`，L30 的边距状态按 element.hashValue 索引。`Utility/Indexed.swift` L3–9 的 Indexed 同时包含 index 与 value，Hashable 为合成实现；因此增长的段落 value 会改变身份，不是只按索引稳定。

### 已核实机制与适用性

可借鉴：把解析得到的渲染值放在模型/渲染缓存层，避免 SwiftUI 每次 body 求值重复解析相同文本；用内容 revision、宽度和样式版本作缓存条件。`Views/Inlines/InlineText.swift` L18–35 将 inline 渲染成 SwiftUI Text，`Renderer/TextInlineRenderer.swift` L109–119 把 AttributedString 转为 Text 组合；这是原生文字显示，不依赖 WebView 整页重载。

但**不能把它描述为 UITextView 的 textStorage 原位增量重绘实现**：这里是 SwiftUI 值重建；M2 内容身份变化仍可让活跃段落子树重新创建。它也没有聊天级 cellID、测高合并或滚动保持协议。建议借鉴解析/渲染分离，在 OpenMinis 保持外层 cell 和 hosting 根身份，先用稳定文本视图持续显示尾部；若引入分段解析，只更新未定稿尾段，已定稿块需由业务定义稳定 ID。不能简单认为空行之前永不再变，Markdown 的表格、列表、引用、Setext 标题等会受后文影响；需要边界测试，必要时流结束后一次完整校正。

**最低 iOS 15 不代表全部 Markdown 功能完整支持 iOS 15。** 在此 checkout：

- `Parser/MarkdownParser.swift` L237–240：iOS 15 的解析扩展不含 table；iOS 16 才加 table。
- `Views/Blocks/BlockNode+View.swift` L22–25：`.table` 只有 iOS 16 分支，若由 DSL/模型直接提供 table node，iOS 15 无对应表格 View；不能以“整段没显示”归因于 TextKit 后才忽略这一分支。
- `Views/Blocks/ParagraphView.swift` L29–37：多图 ImageFlow 需 iOS 16，iOS 15 走 InlineText 等回退。
- `Utility/ResizeToFit.swift` L12–38：iOS 15 用 GeometryReader＋preference 回写尺寸，iOS 16 才走 Layout；并非所有布局都摆脱双阶段状态回写。

因此：可作为普通文字/富文本渲染与预解析的设计参考，不适合直接替换 OpenMinis 的流式层，更不能宣称替换后 iOS 15 表格与复杂段落就一定完整。该 HEAD README 已注明 maintenance mode；本报告不因此推荐另一整库迁移。

## 给 160v64 的最小修复协议

以下是实现建议，本任务未修改源码。

### P0：先拆开绘制、测高、滚动三个通道

1. 网络 token 先合并进消息模型，messageID 不变、contentRevision 增长；主线程消费最新 revision 更新已有文本视图。不得因“高度相同”提前 return 而跳过文字更新。
2. 使用一个 pending/scheduled 标志，按主队列下一轮或显示帧合并测高请求；不是每 token 一个 async 块，也不是只做一直被新 token 延后的 debounce。一次 drain 消费最新 revision，若处理中又来了更新则再安排一次。停止/错误/取消/切会话前按各自语义处理最后状态，正常结束必须 flush 最后文字和最终测高。
3. 在实际有效宽度、字体/字号、inset 与内容版本下测量。宽度未就绪时保留待测请求，不把零宽结果缓存为最终高度。按像素尺度消除微小数值抖动，但不能用不分宽度/内容的“同尺寸熔断”丢掉真实变化。
4. 相同高度只抑制父列表高度失效，不抑制文字绘制；不同高度将对应 messageID 放进待失效集合，在一次更新事务处理。若异步测量，结果须核对 messageID、revision、宽度/样式版本，旧结果不得盖新结果。
5. intrinsicContentSize getter 返回已经确定的缓存；不要在 getter 或重入的 layoutSubviews 里递归 invalidate、修改模型并同步 layoutIfNeeded。保留真实新高度上报，不靠停报高度掩盖循环。
6. 每次几何事务先捕获锚点 messageID/edge/offset 和是否跟随底部，模型与布局原子提交后按新 IndexPath 补偿一次；不要把 scrollToBottom 与锚点恢复同时当成两个控制器。用户拖动期间尊重阅读/手势状态。

### P1：不闪不丢字的原位更新

- 不更换稳定 cell/hosting controller/根 ID，不先清空 text/attributedText，不用 alpha 或插入动画“唤醒”文字。
- 对 UIKit 输出文本视图，仅当内容/样式确有改变时更新；是否使用局部 textStorage 修改由原有渲染器能力决定，并正确批量编辑/失效绘制。不能把 setNeedsDisplay 当作全文未写入或高度被截断的修复。
- 同高追加文字、仅属性变化、结束时切换富文本都要有独立绘制路径；富文本最终替换仍保持外层消息身份，并纳入同一个锚点事务。异步图片/代码高亮完成也走同样的 revision 校验与局部测高通道。
- 中文输入 markedText 同步单独作为补丁测试，不和输出层复用“跳过更新”开关。

### 最小真机验收矩阵

在用户的 iOS 15 与 160v64 基线各跑同样用例，逐项对照，不用编译通过代替视觉验证：

1. 同行持续追加中文/英文（高度不变）和跨行追加（高度变），每个已接收文本最终可见，结束尾字不滞留。
2. emoji/组合字符、代码围栏半截→闭合、列表/标题/长链接、图片延迟载入；iOS 15 表格明确展示回退或限制，不能静默空白。
3. 输出时停留底部、向上读历史、向前插入历史消息、键盘开合/旋转；锚点消息不换，用户上滑不被拉回底部。
4. 中文拼音/九宫格候选、连续选词、删除、粘贴、多行换行、输入中切模型/收到输出；组合串与光标不被旧 binding 覆盖，提交最终字不丢。
5. 极快 token、停止/取消/错误与恢复、切会话、长时间流式；无无限测高或重排。记录同一消息的 contentRevision、测量 revision、paint 次数、height-change 次数和锚点偏移，不记录用户全文。

优先序：**稳定身份与模型/布局事务 → 原位文字独立更新 → 有尾部 flush 的测高合并 → 单一锚点控制 → markedText 输入保护**。三库分别提供了部分依据，没有任何一个库在所审源码中完整实现并证明 OpenMinis 的全部修复。
