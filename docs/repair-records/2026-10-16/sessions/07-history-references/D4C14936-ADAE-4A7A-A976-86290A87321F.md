## 160v64 静态审查结论

**基线：** `/var/minis/workspace/OpenMinis-v64`，产物提交 `f017c76cae19053a86236112544c4185c9e94783`，移植脚本提交 `650adb0`。以下行号均属于此基线，**不是 HEAD**。全程只读，未修改源码、未安装 SDK、未构建。

### 1. Hosting 快速更新分支不可达，且探针把重建误报成快速更新

**位置：**
- `src/ios/iOS15Compat.swift:515–538`：世代号自增、快速分支判等。
- 同文件 `:437–439`、`:572–580`：重建后的身份戳和探针。
- `src/ios/Agent/MessageList/CollectionViewMessageListV3.swift:1392` 等：实际配置调用。

**确定的问题：**

每次 `apply` 都先执行：

```swift
_ios15ApplyGen &+= 1
```

然后才检查：

```swift
_v63ConfigGen == _ios15ApplyGen
```

上次重建结束时，两者已相等；下一次调用先把 `_ios15ApplyGen` 加一，因此判等必然失败。快速分支自身也没有更新身份戳。正常调用链会**一直删除旧宿主并新建 `UIHostingController`**，而不是注释声称的就地更新。

更严重的是，重建分支先将 `_v63ConfigGen` 设置成当前世代，再调用 `_v63ProbeIncr()`；探针此时看到“两者相等”，将重建计入 `fast`。

只读状态演算结果：

```text
10 次 apply：
实际 fast=0，实际 rebuild=10
探针 fast=10，探针 rebuild=0
```

所以历史装机日志中的 `[V63-PROBE] fast=… rebuild=0` **不能证明快速更新真正运行过**。频繁销毁 SwiftUI 宿主会丢失局部状态、重建富文本桥接和尺寸协商，是闪屏及内容突现的高价值线索。

**修复方向：**
- 分开“内容身份”与“更新世代”，使用明确的消息/块身份决定复用或重建，而不是用每次自增后的世代号判等。
- 快速分支和重建分支分别直接调用 `hitFast()`、`hitRebuild()`，不要事后由身份戳猜测走过哪个分支。
- 同身份更新保留宿主并使固有尺寸失效；身份改变时明确重置必要状态。

**静态验证：**
加入宿主生命周期状态测试：同身份连续更新应只创建一次 controller；身份切换才重建；记录的 fast/rebuild 必须等于实际执行次数。现有验证只检查自增、判等、打点“存在”，不足以识别这个错误。

### 2. Hosting 两个测量入口宽度不一致，且 cell 内边距被重复扣除

**位置：**
- `src/ios/iOS15Compat.swift:417–426`：`sizeThatFits` 使用传入宽度。
- 同文件 `:447–488`，尤其 `:473–475`：`systemLayoutSizeFitting` 路径将宽度限制到 `collectionView.bounds.width - 32`。
- 同文件 `:563–570`：实际宿主四边贴父视图，渲染宽度为父宽。
- `src/ios/Agent/MessageList/CollectionViewMessageListV3.swift:344–346`：assistant block 自身再加左右各 16pt。
- 同文件 `:1391`：hosting configuration margins 已为零。
- `src/ios/Agent/MessageList/MessageListLayout.swift:180–203`：cell 属性宽度为 collection view 的完整宽度。

**确定的问题：**

以 390pt 宽的 assistant block cell 为例：

| 路径 | 宿主宽度 | 扣除 block 自带左右 padding 后 |
|---|---:|---:|
| 实际渲染 | 390 | 358 |
| `sizeThatFits(390)` | 390 | 358 |
| `systemLayoutSizeFitting(390)` | 被夹到 358 | 326 |

`-32` 在宿主层扣一次，block 内部 `.padding(.horizontal, 16)` 再扣一次。代码因此拿**比渲染更窄的提议**测高度，两个测量入口也不遵循同一宽度合同。长文本、表格及代码块可能得到不同换行数，进一步污染高度缓存、触发高度纠偏及跳动。

**修复方向：**
- 明确宿主测量宽度代表“完整 cell 宽度”，由 SwiftUI 内容自行消费 padding。
- 将两个测量入口统一到同一个宽度解析方法；只夹异常或超出真实父宽的提议，不在宿主层硬扣内容边距。
- 不要用屏幕宽度代替分屏、旋转后的实际父宽。

**静态验证：**
建立完整宽度、内容宽度的约束演算测试，覆盖 390pt、iPad 分屏及旋转；同一提议下两个测量入口应使用相同宿主宽度。assistant block 的 32pt 边距必须只消费一次。随后真机对照记录测量提议、宿主 bounds 和 TextKit 容器宽度。

### 3. 全表重排“突增节流”只有丢弃，没有尾沿补发，会留下更新过的高度与旧下游帧

**位置：**
- `src/ios/Agent/MessageList/MessageListLayout.swift:519–520`：先写入新高度。
- 同文件 `:642–664`：短时间内再次大幅变化时直接 `return ctx`。
- 同文件 `:671–688`：正常路径才安排异步全表重排。
- 同文件 `:174–205`：后续 cell 的位置、总高度由 `prepare()` 根据高度缓存重算。
- 同文件 `:704`：节流时间表还是按 index 存储的静态全局状态。

**确定的问题：**

非流式 cell 出现一次 `|delta| > 100` 的变化后，会安排全表重排。若此任务已经执行，随后 250ms 内又出现一次大变化：

1. 第二次新高度仍写入 `heightCache`；
2. 节流分支直接返回；
3. **没有安排剩余窗口结束后的重排，也没有标记待补发。**

若之后没有其他事件触发完整 `prepare()`，下游 cell 的旧 `y` 和 `totalHeight` 没有显式收敛机制。代码前面的注释已明确说明：优选属性更新本身不保证刷新所有下游位置；因此这个节流重新引入了它原本要修复的重叠、空洞和滚动后才恢复问题。

只读控制流验证确认：节流返回分支不存在异步调度或待补发状态；两次间隔 100ms 的大变化只安排一次显式全表重排。

**修复方向：**
- 保留高度即时提交，但节流必须是“合并”，而不是直接丢弃。
- 第一次调度后发生的新变化应置 dirty，并保证窗口尾沿至少补一次全表重排。
- 节流状态应属于当前 layout，并随内容身份或 snapshot 重映射处理，不能让不同会话的同 index 相互限流。

**静态验证：**
用可控时钟测试：第一次纠偏执行重排后，在 100ms 内再纠偏，随后停止所有输入；窗口结束后必须还有一次最终重排，并满足：

```text
后一 cell 的 y = 前一 cell 的 maxY + 实际间距
totalHeight = 全部已提交高度与间距之和
```

同时测试两个 layout 实例同 index 的更新互不影响。
