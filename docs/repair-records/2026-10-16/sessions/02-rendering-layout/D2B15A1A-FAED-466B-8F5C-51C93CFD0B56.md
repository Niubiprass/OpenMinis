## 只读审查结论

**最值得优先验证的是两个相互叠加的高度错误，而不是淡入或模型输出：**

1. **工具卡重叠／遮切：V64 的收敛闸可能把工具卡的真实增长当作“旧高度反馈”拦掉。** `CollectionViewMessageListV3.swift:3263–3273` 对工具块一律估高 **36pt**；`MessageListInfrastructure.swift:743–768` 在重新测得高度不低于传入 attributes 高度、且没有更高的 `SelectableMarkdownTextView` 实测高度时，把结果强制改回原高度。工具卡通常没有 Markdown 文本视图，因此“没有 TextKit 新证据”**不等于**“工具卡没有真实增长”。若工具卡展开内容、状态或内嵌终端确实增高，此分支会继续提交旧高度；`MessageListLayout.swift:189–205` 按该高度排下一个 item，`MessageListInfrastructure.swift:46–56` 又裁剪超出 cell 的内容，正好形成卡片交叠或被切。源码注释在 `CollectionViewMessageListV3.swift:1481–1504` 也明确记录了仍在运行的工具块被旧高度播种后与后续卡片重叠的既往路径。**这是一条强代码推断，尚非本次截图的真机实证。**

2. **头像标题与正文间巨大留白：优先查标题后第一个正文 block 的“占位高度大于实际内容”，并区分它与滚动偏移。** 标题本身估高仅 30pt（`CollectionViewMessageListV3.swift:3105–3115`）；列表逐项累加高度决定正文的 y 坐标（`MessageListLayout.swift:189–232`）。所以若“Minis”标题在顶部而正文从半屏开始，必须检查两者之间具体 item 的 `frame.height`、实际内容高度和 footer，而不能只看 `contentOffset`。历史缓存由 index 高度、precalc、estimate 依次主导（`MessageListLayout.swift:193–201`）；旧 item 高度在快照重映射时仅按 item 身份搬运（`:809–835`）。另外，大于 100pt 的缩小，在已有缓存且非 defer 状态下还可能被 **20 秒最大高度锁**拒绝（`:475–493`），足以让先前测大的正文保留一块显著空白。footer 是较小的候选：其正常估高只有 4/48pt（`CollectionViewMessageListV3.swift:3116–3122`），单个 footer 不足以解释“半屏”留白；源码已禁止将 footer 高度写入内容键 memo（`MessageListLayout.swift:927–939`）。

### 重进会话的具体时序风险

`CollectionViewMessageListV3.swift:2022–2065` 在 `isLoadingSession` 结束时清 **layout** 高度缓存、应用快照；若是首次加载，马上执行 `scrollToLastItem()`。该方法只是 `scrollToItem(..., at: .bottom)`（`:4396–4403`），当时离屏 item 多数仍是估高，真实测量和 `contentSize` 后续会变。代码以 content-size KVO、底部 pin 和 8 秒 clamp 补救（`:1225–1276`, `:2053–2062`），但这些处理的是**滚动落点**，不能修复某个正文／工具 cell 自身错高。

更具体的重入竞争在 `:3434–3493`：相同 item ID 会跳过 diffable apply；源码注释记录过 `flushPending(updateUIVC-backstop)` 先于 `bind3-sessionLoad` 应用，后者清了 layout 缓存却遇到 SKIP，已可见 cell 仍持有旧的 `lastComputedHeight`。目前 SKIP 对 `bind3-sessionLoad` 调用了 `remeasureVisibleCells`（`:3489–3492`），函数会清**可见** cell 与 layout 高度再 reconfigure（`:2466–2483`）；这是已存在的针对性缓解，不应误报成“完全没有 invalidate”。但离屏内容依赖重新配置与内容键 memo：`configureCell` 从 memo 播种（`:1447–1453`, `:1523–1544`），cell 在同宽时优先返回自身缓存／播种高度（`MessageListInfrastructure.swift:319–329`, `:435–469`）。内容键对 block 只含 message ID、block ID 和 **字符数**（`CollectionViewMessageListV3.swift:4033–4051`）；工具状态／展开态、同长度内容变化未必改变它。虽然异步附件另有 render-qualified key，仍须核实工具状态是否进入该资格键。由此，**重进后旧高度重新播种 + 可见 cell 未及时得到正确新尺寸**是应与 V64 收敛闸并查的路径。

`SelectableMarkdownView.swift:5484–5524` 在 iOS 15 以 `sizeThatFits` 和 `intrinsicContentSize.height` 对外报高；`:9366–9442` 又以正文长度、宽度、表格 generation 作为复测指纹。它解释正文 TextKit 与 SwiftUI 高度可能不同，但**不能替工具卡提供新高度**。其首次纠偏只在文本实测比 cell **更高** 8pt 以上触发（`:9725–9755`），因此不能指望这条路径消除标题下已经占多的空白。

## 最小安全修复建议（仅建议，未修改）

- **先修工具卡收敛闸的适用范围**：`MessageListInfrastructure.swift:759–766` 不应以“没有更高的 Markdown TextKit 高度”否定**非 Markdown 工具 cell** 的实测增长。最小方向是仅对已识别为 Markdown 文本、且有可比的稳定 TextKit 实测依据的 cell 启用 V64 hold；工具卡及其他非文本 cell 采用实际 `systemLayoutSizeFitting` 结果，同时保留原有防自激保护并观测是否出现单调累加。不要全局删掉 V64 闸：`:561–579` 注释记录了 iOS 15 先前真实发生的测量反馈膨胀。
- **在会话加载完成／相同 ID 跳过 apply 的边缘做定点双侧失效**：维持现有 `remeasureVisibleCells`，核验调用时机在最新内容配置完成之后；对检测到工具状态、展开态或正文版本改变的 item，同时使 layout 高度／memo 和可见 cell 自身缓存失效，并 reconfigure 对应 item。不要把每次滚动改成全表 `clearHeightCache`／同步全表测量：当前代码已有避免 hosting graph 重入与性能回退的理由。
- **内容键须反映会影响高度的工具展示状态**，或在该状态变化时直接淘汰相应 memo；不能只依赖 `content.count`。同时检查 `MessageListLayout.swift:475–493` 的 20 秒 flip-lock 是否在**真正内容收缩**时阻挡大幅回落；宜以稳定内容／展示版本变化绕过，而不是取消所有防振荡。

## 建议的验证方式

在可复现的 iOS 15 真机上，重进同一历史会话并记录“标题—首个正文—连续工具卡”的 **item ID、index、layout attributes 的 y/height、cell bounds.height、`systemLayoutSizeFitting` 高度、`contentOffset.y`、`contentSize.height`**。若标题 frame 正常、正文前某个 item 的 layout 高度远大于其实际内容，证实留白是行高；若所有相邻 frame 连续但屏幕整体平移，再查 `scrollToLastItem`／底部 inset。关注已有 `[BottomGapDiag][stale-height]`（`MessageListInfrastructure.swift:686–692`）、`[CellSizing][V64-CONVERGE]`（`:759–765`）、`[CellSizing][V31-FLIPLOCK]`（`MessageListLayout.swift:475–493`）、`[FGLayout] remeasure`（`CollectionViewMessageListV3.swift:2466–2483`）和 `SnapshotDiag SKIP`（`:3434–3493`）。尤其要看工具卡出现 **`recomputed > est` 且 `tk=0`、随后 hold 原高**，以及正文出现 **held > needs** 的记录；再对比离开重进、工具展开／收起、滚动到离屏再返回三种情形。上述诊断区分因果所需；仅凭截图无法断言是哪一项先触发。
