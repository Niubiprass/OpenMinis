### 一、必须纠正的结论

**此前“256000 未按 128k 模型窗口裁剪，所以一直等到 217600 才压缩”的断言，与当前源码不符。**

这里有三个不同概念：

1. **模型/组有效窗口**
   - `src/ios/Agent/Chat/AIChatViewModel+Misc.swift:280–297`
   - `native = model.contextWindowTokens`。
   - 读取当前会话绑定组的 `contextLimitTokens`；有效窗口为模型窗口与有效组上限的较小值。
   - `Int.max` 为“不限制”哨兵。
   - 组上限不低于模型窗口时，不会抬高模型窗口，且 `isUserCap=false`。
   - 仅会话绑定 `.group` 时读取组限制，直接模型绑定不使用组上限。

2. **用户自动压缩软预算**
   - `src/ios/Agent/Chat/ContextPolicy.swift:194–206`
   - 明确实现：
     ```swift
     effectiveTokens = window > 0 ? min(tokens, window) : tokens
     threshold = max(1, floor(effectiveTokens * 85 / 100))
     reached = enabled && measured >= threshold
     ```
   - 因而模型/组有效窗口若为 **128000**、用户预算为 **256000**，软预算压缩线是 **108800**，不是 217600。
   - 如果实际配置为 **131072**，软预算线则是 **111411**。截图“128k”的显示精度不能替代原始配置值。
   - 85% 是硬编码的比例，而非独立可配置比例。

3. **独立的模型安全压缩线**
   - `ContextPolicy.swift:32–73, 89–116`
   - 绑定的用户组上限：85% 压缩、70% 卸载、55% 卸载目标。
   - 无绑定上限的原生窗口：
     - `<32000`：不自动压缩；
     - `32000…<64000`：通常只卸载、耗尽提示；
     - `64000…<128000`：压缩线为窗口减 10000；
     - `>=128000`：压缩线为窗口减 20000。
   - **128000 原生窗口的安全压缩线是 108000，比软预算的 108800 更早。**
   - `AIChatViewModel.swift:6388–6392` 只有安全判断为 `.ok` 时，才附加检查软预算。因此不能笼统说“所有压缩都在 85%”。

“真实窗口”在这里准确说是**客户端解析到的模型配置窗口**，并非运行时向服务端验证的真实容量。`src/ios/Providers/LLMTypes.swift:797–846` 优先使用明确的 `contextWindow`，缺失时按模型 ID 猜测，未知模型回退为 128000。如果代理真实限制与本地配置不符，`min()` 也无法凭空获知。

### 二、token 计数及工具输出实际处理

**发送判断不是直接拿上一次 API usage、累计账单 token 或界面字符数比较。**

- `AIChatViewModel+Compaction.swift:118–133`：
  ```text
  measured = calibrationRatio ×
             (estimate(effectiveAgentHistoryUncounted()) + contextFixedTokens)
  ```
  使用压缩标记生效后的出站历史，因此成功压缩、卸载后会重新估算，而不是继续使用压缩前 usage。
- 同文件 `140–148`：记录实际派发请求的估算及模型/窗口，以供返回 usage 校准。
- `ContextPolicy.swift:282–325`：
  - 文本是字符类别启发式估算，不是服务端精确 tokenizer；
  - 工具调用计入工具名及输入 JSON；
  - 工具结果计入工具名、**完整结果字符串**及图片估算；
  - 每消息、每工具部分还有结构开销。
- `ContextPolicy.swift:369–380`：固定部分包括系统提示、工具名/描述/参数说明等估算。
- `AIChatViewModel.swift:2314–2317, 6360`：发送前可先初始化基础固定部分；循环中用当前系统提示及工具重新计算。
- `ContextPolicy.swift:397–404`：校准比率限制在 `0.8…3.0`。因此仍可能误差，不能称为精确 token 统计。
- `AIChatViewModel+Compaction.swift:113–117`：容量测量故意不执行会写盘的图片请求预算处理，实际图片处理与估算仍可能有差异。

**工具输出有卸载机制，但不是任何大输出都立即消失。**

### 三、SSL/网络失败后究竟怎样处理

#### 1. 单次摘要调用没有 TLS 自动重试或按网络错误切模型

- `AIChatViewModel+Compaction.swift:1460–1494`：
  - `CancellationError`、`LLMError.networkError`、`NSURLErrorDomain`（含 TLS/DNS/超时）都**不进行分段重试**；
  - 限流、密钥错误、超时类 transient 也不靠切半解决。
- 同文件 `1582–1617`：摘要模型 fallback 只捕获 `isFallbackable` 或服务端 5xx 容量类错误。
- `src/ios/Providers/LLMError.swift:74–96`：`networkError` 的 `isFallbackable=false`。
- 因而标准 TLS/网络错误会退出当前摘要调用，不会因为这条错误进行分段、切模型或退避重试。

注意：上述结论依赖错误被正确归类。若某代理把“SSL”包装成普通 `providerError` 文本，可能走另一条分支；截图文字本身不能证明运行时错误类型。

#### 2. 摘要失败不提交新的摘要标记，但错误被吞入状态行

- `AIChatViewModel+Compaction.swift:1088–1122`：
  - 摘要异常设置 `Compaction failed: …` 后直接 `return`；
  - 标记计算/提交发生在后面，失败不会沿成功路径覆盖摘要。
- 同文件 `1030–1034`：`defer` 恢复处理中状态。
- 函数没有将“网络失败/成功/取消”作为结构化结果返回给调用方。

#### 3. “没有 TLS 重试”不等于“一次失败后整条发送链立即停止”

- **发送前自动压缩**：
  - `AIChatViewModel.swift:2920–2937` 在自动压缩开启时走 `compactAndSend()`。
  - `AIChatViewModel+Compaction.swift:399–413`：即使压缩失败，只要未取消，仍安排队列继续 drain。这是源码明确保留的行为。
  - 队列进入 agent loop 后，还会经过循环安全门，可能再触发一次摘要尝试。**因此同次用户发送可能看到重复 SSL 失败，但不是摘要网络层的退避重试。**
- **循环内压缩**：
  - `AIChatViewModel.swift:6403–6421`：压缩前后重新测量；失败通常表现为没有缩小，并停止继续反复压缩。
  - 软预算失败：记为 no progress，重新检查真实窗口后允许继续。
  - 安全压缩失败：`6477–6503` 按窗口决定：
    - 仍在窗口内：允许继续请求；
    - 只是校准外推超窗、原始估算仍可容纳：允许一次试探；
    - 确实无法容纳：停止 loop，设置 `canResume=true`，显示“上下文满且不能进一步压缩，请新会话或清空”。
  - 每循环压缩次数上限为 3：`AIChatViewModel.swift:133`。

所以，“SSL 压缩失败 → 历史未缩小 → 再判断已满 → 提示新会话”**符合当前源码可能路径**。目前不能据此确定用户当时就是这条路径，更不能归因为预算未裁剪。

### 四、实际确定的问题与待验证风险

**源码可确定：**

1. **失败类型没有传回调度层。** 网络失败、摘要增大、没有可压缩内容等都可能归为“没进展”，最后统一提示 Context Full。用户无法清楚区分“窗口真的无解”和“网络暂时无法生成摘要”。相关位置：`Compaction.swift:1101–1121`、`AIChatViewModel.swift:6408–6421, 6496–6503`。
2. **compact-and-send 在压缩失败后仍继续队列**，可造成同一发送链再次尝试压缩或继续一次本来用户以为已中止的发送。位置：`Compaction.swift:399–413`。这是现有设计，不应误报为“失败立刻完整中断”。
3. **摘要预检与正常计数口径不一致。** `Compaction.swift:1680–1693` 使用 `conversationText.count / 4 + 800`，尤其对中文明显偏低；普通容量判断却用字符分类及校准。分段能补救部分服务端超长拒绝，但无法保证首次摘要请求可容纳。
4. **分段重试漏传旧摘要。** `Compaction.swift:1368–1370` 首次拼入 `previousSummary`，但 `1409–1411` 对两个半段递归时均未传入它。若已有压缩标记且本次进入分段，返回的拼接摘要可能不再包含旧摘要的信息。这是独立的摘要连续性缺陷，不是 SSL 根因。
5. **设置页显示的是输入预算理论值。** `src/ios/Views/ContentView.swift:8795, 8811–8812` 虽说明较小模型/组优先，但预览直接显示 `value * 0.85`。输入 256000 会显示 217600，不是当前会话实际压缩线；不能拿该预览证明执行层未裁剪。

**尚不能确定：**

- 用户当时安装版本是否包含当前软预算实现；
- 截图 128k 是明确配置、组限制还是未知模型回退；
- SSL 错误的 `NSError` domain/code、失败 provider、证书链或代理原因；
- 当次 measured/history/fixed/ratio、是否刚得到超大工具结果、是否已进入 no-progress 分支；
- 校准或窗口元数据是否误判了实际服务端容量。

### 五、最小修复建议

1. **不要重复增加已有的 `min()` 修复。** 保留现有预算裁剪；先补会话可见诊断：模型配置窗口、组上限、软预算、软线、安全线、measured、校准来源。
2. 将 `compactBefore` 改成返回结构化结果，例如 `success / cancelled / failed(reason)`；调度层单独处理网络故障，不把它伪装为无法再缩小。
3. compact-and-send 遇网络失败时默认保留待发送内容并显示“重试压缩”，不要无条件立即 drain；软预算失败但安全窗口仍足够的情况，可以明确允许继续。
4. 如增加网络重试，只对可恢复断连/超时做有上限退避；TLS 信任、证书错误不能靠无限重试，更不能关闭证书校验。
5. 摘要预检复用 `ContextSizeMeter`，计入真实摘要系统提示/包装，并预留输出空间。
6. 分段时将旧摘要传给首段一次，保证不会遗漏，也避免每段重复加入。
7. 设置页将现有值标注为“仅按输入预算计算”；会话内显示真正生效阈值及安全门可能提前触发的原因。
