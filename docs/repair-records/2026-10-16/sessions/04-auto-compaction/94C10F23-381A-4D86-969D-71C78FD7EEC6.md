## 3. 产品语义与策略分离

### 3.1 两个容量概念

- `W`：`resolvedContextWindow(for: resolveCurrentEntry().model).window`，已考虑更低模型覆盖与 group cap，代表现有容量/安全策略基础。
- `B`：用户设置的全局正整数软预算，建议缺省 `256000`，单位 tokens，不用二进制 Ki token 换算。
- `E = min(B, W)`（W 已知且 > 0）；W 未知时 E = B。**绝不能 E=0，也不能把 Int.max 当小窗口。**
- `T = floor(E × 85 / 100)`；E=256000 → **217600**。纯整数计算应防乘法溢出：使用商余数或限制 B 的可配置范围，不直接允许任意 Int 值乘 85。
- `measured >= T` 触发（217599 不触发，217600 触发）。预算包含 effective history、摘要和 system/tools 固定开销，沿用本地校准后的 outbound measured，不是消息正文长度。

### 3.2 开关只控制主动软预算，不关闭安全系统

- enabled = false：**整个原安全决策链保持原样**，包括发送前提示、shortcut 无 UI 分支、in-loop 自动安全压缩、offload、真实超窗停止/恢复。
- enabled = true：额外增加 E 的 85% 主动压缩，正常用户界面不弹 near-capacity 确认。
- 原安全线可能先于 T（小原生窗口/已有 group 比例线），仍先执行原安全策略；85% 不是“必须等到此线才可以做任何安全处理”。
- 软预算不是输出 max_tokens 硬上限，不改变 provider 请求窗口、不将超过 B 定义为 Context Full、不保证单条巨型输入一定能压进 B。
- MVP 不增加独立“压后必须到 55%”承诺；目标是一次压缩明显缩小，尽量低于 T。固定提示、当前回合和必要摘要本身可能超预算，此时仍按 W 判断能否继续。

### 3.3 默认与旧偏好迁移

推荐**复用原键 `autoCompactOnThreshold` 作为 enabled**，不再造第二个同义 Bool：

1. 有原键 true/false：保留用户选择，升级不擅自反转。旧 true 表示允许自动压缩，现在也承担软预算 opt-in，设置页说明这一点。
2. 原键缺失：默认 false，维持 v64 既有 opt-in 语义；如产品明确要求新装默认开启，应另写验收规则，不能把缺省 false 当未设置后无条件覆盖所有旧用户。
3. 新增键建议 `context.autoCompact.budgetTokens`，缺失取 256000；读到零、负数、类型异常时回退默认，不落成“零容量”。UI 保存和 CLI 写入校验同源。
4. 因为全局偏好在 UserDefaults，不需动 ProviderConfigDB.schemaVersion、ModelGroup.CodingKeys、ChatStore 或 CompactMarker schema；也不承诺自动参与 provider CloudKit 同步/备份。
5. 为消除“持久化了但已打开会话不变”，把 VM 的 autoCompactEnabled 改为统一 preferences 的 live getter/setter；Settings 用同键 @AppStorage，VM 如须刷新观察视图则转发 defaults 变化或采用共享 ObservableObject（可参考 `src/ios/Providers/Voice/VoiceProviderResolver.swift` 中 `VoiceOutputState`）。预算每次决策 live read，不能只在 VM.init 缓存。

### B. 决策必须保留触发原因

建议增加小型决策包装，而不是给 CheckResult 乱加全局意义：

```text
ContextCompactionDecision:
    safetyVerdict: 原 ContextPolicy.CheckResult
    softBudgetReached: enabled && measured >= T
    reason: safety / budget / none
```

`checkContextBeforeSend(site:)` 可保留为兼容 wrapper，新的 helper 返回上述决策，统一只测量一次。

- 原 safetyVerdict != ok：完全复用原处理（安全优先，特别保留 exhausted）。
- 原 safetyVerdict == ok 且 softBudgetReached：走非阻塞预算压缩。发送前可复用 pendingSendText/attachments + compactAndSend；循环内复用原 guard 的压缩后测量/新 bubble/turnCount bookkeeping。
- 预算原因不能简单复用 needsCompact 再让原 false 分支弹安全确认，也不能让安全原因因 enabled=false 被跳过。
- 预算压缩失败、无可压历史或无进展：不制造 exhausted，不反复拦住同一 send；若 W 仍允许，继续真实请求。`maxInLoopCompactions=3` 与 no-progress 保护保留；建议软触发不耗尽原安全压缩机会，至少将“软无可压/软无进展”与“安全无进展”分开记录。

### C. 原始聊天保留与有损摘要

- **直接复用** `compactBefore` 成功路径：新建 marker、`cachedLatestMarker=marker`、保留 agentHistory 与原消息行，inference 时合成摘要；原消息只灰显。`revertCompact()` 已可回到上一 marker。
- 不新增 DELETE/UPDATE 原聊天内容、不将摘要覆盖 raw_messages、不对 agentHistory.removeSubrange 做压缩。
- `generateCompactSummaryOnce` 现有 prompt 的 “MUST PRESERVE (never omit or shorten): All file paths ... Commands ...” 过于绝对，可能与允许有损相冲突。最小版本可以先保留保守 prompt并在 UI 诚实提示“摘要可能丢失细节”；如主动加大有损程度，给预算原因单独 profile：保留当前任务约束、关键状态/路径/决策/最近结果，允许省略重复输出和旧枝节，不虚构任务，别把原消息当新指令。不要全局粗暴改成“丢弃所有工具结果”。
- 自动预算增加摘要频率，会额外调用模型、消耗 tokens、重建缓存；设置说明应明确。

### D. 必须处理的两个隐藏缺口

#### D1. 主动预算不应把正在执行的整回合摘要掉

目前安全 in-loop guard 直接选最后活动 UI 消息，`compactBefore` 将其及以前内容归入摘要，之后新建 assistant bubble。这是既有紧急行为，不是“保留当前回合”的自动保证。若预算软线也无脑复用，当前用户指令会被改写成 past tense 摘要，后续工具阶段可能忘记当前工作。

推荐对**预算原因**的循环内压缩增加安全边界选择：

1. 用 `isUserBubbleEntry` 找到本次真实任务输入；对一次 run 记录起始用户的 db id/稳定位置，而不是把每个 tool_result user 当新回合；有中途队列注入时，宁可保留整个 run 的活动范围。
2. 摘要右边界只选该回合起点**之前**、已经落库的最后完整消息。当前回合的 user、assistant tool_use、对应 tool_result、真实请求所需 reminder 全部留在 post-anchor。
3. **不能仅更换传入 compactBefore 的 UI UUID 就认为完成。** 819 行以后的源码在 UI `sourceSortOrder` 缺失时，会回退到 `agentHistory.last(where: dbMessageId != nil)`（约 892 行），即仍然跨进当前回合。应为预算路径给 compactBefore 增加可选明确 raw/db anchor 参数，或抽取一个 raw-anchor 内部入口；用 `agentHistory` 和 DB 同时验证该 id，预算路径解析失败就 defer，禁止退到历史尾部。原手动/安全路径保留现有回退。
4. 如果旧 marker 已覆盖边界、没有较早已落库完整回合或未完成工具链横跨候选边界，软压缩本轮跳过，等待回合结束/下一次发送；不要产生等价 marker、空范围或伪“上下文满”。
5. 原生窗口真的逼近 W 时仍允许既有安全路径处理当前长回合，不能为了保护软预算目标禁用安全压缩。

发送前 `compactAndSend` 已将新输入排队、排除 queued bubble，通常可安全地只摘要旧历史；保持 `pendingSendIsFromComposer` 和附件映射，不把 CLI/shortcut/job prompt 恢复到用户草稿。

#### D2. warm-up 必须感知软线，但不能每次滑动

`effectiveAgentHistoryUncounted` 在 2145 行附近，对 v2 marker 的 pre-anchor warm-up 只决策一次并缓存 `warmUpDropByMarker[marker.id]`。默认会带回最近几轮原文；这批历史可能把刚获得的压缩空间吃掉。

- `trimWarmUpToFit` 的可选 warm-up 空间线建议取 `min(原安全 compact line/窗口, 当前启用预算的 T)`，扣除校准比率、system/tools 固定量、summary 与完整 post-anchor。不可丢 post-anchor 当前回合来满足预算。
- 裁剪只能在真实用户回合边界进行，沿用 ContextSizeMeter.warmUpDrop / walkBackUserTurnsBounded 的工具配对边界规则。
- 同一个 marker 的裁剪决定保持稳定；不要每轮因为 rest 增长就向前挪一轮，避免 prefix 改变导致 prompt cache 一直失效。
- 预算/开关/模型/绑定 group limit 的**实际配置变化**时，清掉相关缓存或把这些配置值纳入缓存 key；否则用户降低预算后仍沿用旧 drop。仅使用 broad configRevision 作 key 会因无关配置也反复丢缓存，优先用有效参数。
- 当固定提示 + summary + 当前回合已超过 T，warm-up 可以全部移除，但仍按 W 决定发送或停止；软线不要求强行归零。

## 5. 最容易破坏的 invariants

### 工具调用配对

1. tool_result 是 user-role，不代表真实用户回合；截断不能发生在 assistant(tool_use) / user(tool_result) 中间。
2. 对 Responses 组合 id（`call_id|fc_id`），沿用 `pairingKey` 的 call_id 归一化，不能直接比较整个字符串导致假孤儿。
3. `dropOrphanedToolParts` 会丢没有 use 的 result，并为历史上无 result 的 use 合成 interrupted error；**最后 assistant 的 tool_use 豁免**，因为可能正处于发起工具与结果加入之间。不能在这里用自动压缩把仍将执行的工具提前判失败。
4. pre-anchor 裁剪/重放已会裁掉大型结果及配对的 use，摘要拼接之后仍须走现成 `effectiveAgentHistory()` 修复出口；不要直接把 uncounted 结果拿去 provider。

### 当前回合、取消与队列

1. 非循环压缩必须 `startCompactTask`，Stop 才能取消；循环内压缩留在原 currentTask 中 await，不能用 schedulePostCompactDrain 再启动第二条 loop。
2. 保留 `compactBefore` 进入时 isProcessing 的恢复语义；in-loop 若被重置为 false，会允许 DB reload 与 streaming bubble 脱离。
3. 复用 guard 的压缩后 fresh assistant bubble，重置 msgIdx/runMsgId/committedBlockCount，否则新内容追加在 divider 上方灰色旧泡泡。
4. 管理空间的 continue 需要 `turnCount -= 1` 抵消 defer，但**不能重置**整个 maxAgentTurns，防止无限任务。
5. await 摘要期间可能删除聊天、重载/换模型；用 raw id 复验、已有索引夹紧及 cancellation 检查，不跨 await 依赖旧数组下标。未能落库的 anchor 不写 marker。

### usage、预算与安全

1. 使用 `contextMeasurement().measured = ratio × (effective outbound history + fixed system/tools)`；不用 sessionInputTokens 累计数、最后 bubble usage 或 raw agentHistory 全量大小。
2. 不恢复 `max(estimate, lastAPIReport)`：旧 usage 描述压缩前请求，会使摘要后持续假超窗、连续压缩并停机。
3. 保留 `recordContextDispatch` 与相同请求 usage 的配对，模型回退按真正 served model 校准；新预算不得修改 lastDispatchWindow，使服务端 overflow 错误错误地归因到预算。
4. 第一轮尚未构造实际 prompt 时先 ensureContextFixedTokens；in-loop 在 offload 后再测软线；压缩成功调用 announceContextUsageAfterCompaction，避免 UI 还显示压缩前百分比。
5. 使用 resolved 当前 entry，不使用 selectedModel、旧 group resolvedEntryId 镜像或全 group 最小窗口；需求是预算与**实际所用模型 + 绑定 group cap**的最小值，不是所有候选模型中的最小值。真正 fallback 后重算即可。
6. 软失败应只阻止同类无意义重试，不可抑制稍后增长到真实安全线时的压缩机会。

## 3. 产品语义与策略分离

### 3.1 两个容量概念

- `W`：`resolvedContextWindow(for: resolveCurrentEntry().model).window`，已考虑更低模型覆盖与 group cap，代表现有容量/安全策略基础。
- `B`：用户设置的全局正整数软预算，建议缺省 `256000`，单位 tokens，不用二进制 Ki token 换算。
- `E = min(B, W)`（W 已知且 > 0）；W 未知时 E = B。**绝不能 E=0，也不能把 Int.max 当小窗口。**
- `T = floor(E × 85 / 100)`；E=256000 → **217600**。纯整数计算应防乘法溢出：使用商余数或限制 B 的可配置范围，不直接允许任意 Int 值乘 85。
- `measured >= T` 触发（217599 不触发，217600 触发）。预算包含 effective history、摘要和 system/tools 固定开销，沿用本地校准后的 outbound measured，不是消息正文长度。

### 3.2 开关只控制主动软预算，不关闭安全系统

- enabled = false：**整个原安全决策链保持原样**，包括发送前提示、shortcut 无 UI 分支、in-loop 自动安全压缩、offload、真实超窗停止/恢复。
- enabled = true：额外增加 E 的 85% 主动压缩，正常用户界面不弹 near-capacity 确认。
- 原安全线可能先于 T（小原生窗口/已有 group 比例线），仍先执行原安全策略；85% 不是“必须等到此线才可以做任何安全处理”。
- 软预算不是输出 max_tokens 硬上限，不改变 provider 请求窗口、不将超过 B 定义为 Context Full、不保证单条巨型输入一定能压进 B。
- MVP 不增加独立“压后必须到 55%”承诺；目标是一次压缩明显缩小，尽量低于 T。固定提示、当前回合和必要摘要本身可能超预算，此时仍按 W 判断能否继续。

### 3.3 默认与旧偏好迁移

推荐**复用原键 `autoCompactOnThreshold` 作为 enabled**，不再造第二个同义 Bool：

1. 有原键 true/false：保留用户选择，升级不擅自反转。旧 true 表示允许自动压缩，现在也承担软预算 opt-in，设置页说明这一点。
2. 原键缺失：默认 false，维持 v64 既有 opt-in 语义；如产品明确要求新装默认开启，应另写验收规则，不能把缺省 false 当未设置后无条件覆盖所有旧用户。
3. 新增键建议 `context.autoCompact.budgetTokens`，缺失取 256000；读到零、负数、类型异常时回退默认，不落成“零容量”。UI 保存和 CLI 写入校验同源。
4. 因为全局偏好在 UserDefaults，不需动 ProviderConfigDB.schemaVersion、ModelGroup.CodingKeys、ChatStore 或 CompactMarker schema；也不承诺自动参与 provider CloudKit 同步/备份。
5. 为消除“持久化了但已打开会话不变”，把 VM 的 autoCompactEnabled 改为统一 preferences 的 live getter/setter；Settings 用同键 @AppStorage，VM 如须刷新观察视图则转发 defaults 变化或采用共享 ObservableObject（可参考 `src/ios/Providers/Voice/VoiceProviderResolver.swift` 中 `VoiceOutputState`）。预算每次决策 live read，不能只在 VM.init 缓存。

## 4. 最小实现改动清单

### A. 配置和纯策略

- 在现有 `src/ios/Agent/Chat/ContextPolicy.swift` 增加独立 `AutoCompactionPreferences`（可注入 UserDefaults）与 `AutoCompactionBudget`/纯函数；不要改现有 tier 默认值。
- 至少提供 enabled、budgetTokens、effectiveBudget(window:)、triggerThreshold(window:)；纯计算可放此现有 Foundation 文件，减少 project.pbxproj 文件注册风险。
- 在 `AIChatViewModel.swift` 原 autoCompactEnabled 位置改为代理统一偏好；原弹窗按钮继续通过它写相同键。
- 可选 `ConfigRegistry+Builtins.swift/registerChat` 注册 `chat.autoCompact.enabled`、`chat.autoCompact.budgetTokens`，同一底层键和相同缺省值。如果使用共享 observable state，CLI writer 必须经过该 state 或通过 defaults observer 通知，不能写后 UI 假装未变。

### B. 决策必须保留触发原因

建议增加小型决策包装，而不是给 CheckResult 乱加全局意义：

```text
ContextCompactionDecision:
    safetyVerdict: 原 ContextPolicy.CheckResult
    softBudgetReached: enabled && measured >= T
    reason: safety / budget / none
```

`checkContextBeforeSend(site:)` 可保留为兼容 wrapper，新的 helper 返回上述决策，统一只测量一次。

- 原 safetyVerdict != ok：完全复用原处理（安全优先，特别保留 exhausted）。
- 原 safetyVerdict == ok 且 softBudgetReached：走非阻塞预算压缩。发送前可复用 pendingSendText/attachments + compactAndSend；循环内复用原 guard 的压缩后测量/新 bubble/turnCount bookkeeping。
- 预算原因不能简单复用 needsCompact 再让原 false 分支弹安全确认，也不能让安全原因因 enabled=false 被跳过。
- 预算压缩失败、无可压历史或无进展：不制造 exhausted，不反复拦住同一 send；若 W 仍允许，继续真实请求。`maxInLoopCompactions=3` 与 no-progress 保护保留；建议软触发不耗尽原安全压缩机会，至少将“软无可压/软无进展”与“安全无进展”分开记录。

### C. 原始聊天保留与有损摘要

- **直接复用** `compactBefore` 成功路径：新建 marker、`cachedLatestMarker=marker`、保留 agentHistory 与原消息行，inference 时合成摘要；原消息只灰显。`revertCompact()` 已可回到上一 marker。
- 不新增 DELETE/UPDATE 原聊天内容、不将摘要覆盖 raw_messages、不对 agentHistory.removeSubrange 做压缩。
- `generateCompactSummaryOnce` 现有 prompt 的 “MUST PRESERVE (never omit or shorten): All file paths ... Commands ...” 过于绝对，可能与允许有损相冲突。最小版本可以先保留保守 prompt并在 UI 诚实提示“摘要可能丢失细节”；如主动加大有损程度，给预算原因单独 profile：保留当前任务约束、关键状态/路径/决策/最近结果，允许省略重复输出和旧枝节，不虚构任务，别把原消息当新指令。不要全局粗暴改成“丢弃所有工具结果”。
- 自动预算增加摘要频率，会额外调用模型、消耗 tokens、重建缓存；设置说明应明确。

### D. 必须处理的两个隐藏缺口

#### D1. 主动预算不应把正在执行的整回合摘要掉

目前安全 in-loop guard 直接选最后活动 UI 消息，`compactBefore` 将其及以前内容归入摘要，之后新建 assistant bubble。这是既有紧急行为，不是“保留当前回合”的自动保证。若预算软线也无脑复用，当前用户指令会被改写成 past tense 摘要，后续工具阶段可能忘记当前工作。

推荐对**预算原因**的循环内压缩增加安全边界选择：

1. 用 `isUserBubbleEntry` 找到本次真实任务输入；对一次 run 记录起始用户的 db id/稳定位置，而不是把每个 tool_result user 当新回合；有中途队列注入时，宁可保留整个 run 的活动范围。
2. 摘要右边界只选该回合起点**之前**、已经落库的最后完整消息。当前回合的 user、assistant tool_use、对应 tool_result、真实请求所需 reminder 全部留在 post-anchor。
3. **不能仅更换传入 compactBefore 的 UI UUID 就认为完成。** 819 行以后的源码在 UI `sourceSortOrder` 缺失时，会回退到 `agentHistory.last(where: dbMessageId != nil)`（约 892 行），即仍然跨进当前回合。应为预算路径给 compactBefore 增加可选明确 raw/db anchor 参数，或抽取一个 raw-anchor 内部入口；用 `agentHistory` 和 DB 同时验证该 id，预算路径解析失败就 defer，禁止退到历史尾部。原手动/安全路径保留现有回退。
4. 如果旧 marker 已覆盖边界、没有较早已落库完整回合或未完成工具链横跨候选边界，软压缩本轮跳过，等待回合结束/下一次发送；不要产生等价 marker、空范围或伪“上下文满”。
5. 原生窗口真的逼近 W 时仍允许既有安全路径处理当前长回合，不能为了保护软预算目标禁用安全压缩。

发送前 `compactAndSend` 已将新输入排队、排除 queued bubble，通常可安全地只摘要旧历史；保持 `pendingSendIsFromComposer` 和附件映射，不把 CLI/shortcut/job prompt 恢复到用户草稿。

#### D2. warm-up 必须感知软线，但不能每次滑动

`effectiveAgentHistoryUncounted` 在 2145 行附近，对 v2 marker 的 pre-anchor warm-up 只决策一次并缓存 `warmUpDropByMarker[marker.id]`。默认会带回最近几轮原文；这批历史可能把刚获得的压缩空间吃掉。

- `trimWarmUpToFit` 的可选 warm-up 空间线建议取 `min(原安全 compact line/窗口, 当前启用预算的 T)`，扣除校准比率、system/tools 固定量、summary 与完整 post-anchor。不可丢 post-anchor 当前回合来满足预算。
- 裁剪只能在真实用户回合边界进行，沿用 ContextSizeMeter.warmUpDrop / walkBackUserTurnsBounded 的工具配对边界规则。
- 同一个 marker 的裁剪决定保持稳定；不要每轮因为 rest 增长就向前挪一轮，避免 prefix 改变导致 prompt cache 一直失效。
- 预算/开关/模型/绑定 group limit 的**实际配置变化**时，清掉相关缓存或把这些配置值纳入缓存 key；否则用户降低预算后仍沿用旧 drop。仅使用 broad configRevision 作 key 会因无关配置也反复丢缓存，优先用有效参数。
- 当固定提示 + summary + 当前回合已超过 T，warm-up 可以全部移除，但仍按 W 决定发送或停止；软线不要求强行归零。

### E. Settings 与 iOS15 接入

最小视觉交付：在 `src/ios/Views/ContentView.swift` 的 SettingsSheet / Agent Runtime 下加入一个 NavigationLink，页面使用原生 List/Form：

- 标题“自动压缩上下文”；全局 Toggle，能关闭。
- 数字输入“上下文预算（tokens）”，默认显示 256000；可选 128000/256000/512000 等快捷项，但要允许精确 256000，不能只有 256×1024。

- 说明“优先摘要较早历史，摘要可能丢失细节；原始聊天保留。预算是软目标；关闭后仍会在接近模型窗口时执行原有保护。”
- 数字键盘仍需完成/保存入口（iOS15 numberPad 没 Return）。使用 String 草稿，保存时做 Int 解析、合法性校验与错误提示；不把半输入的空字符串写成 0。
- 新 View 可定义在 `ContentView.swift` 以减少 PBX 修改；更清洁方案新增 `src/ios/Views/Settings/AutoCompactionSettingsView.swift`，同步添加 `src/ios/Minis.xcodeproj/project.pbxproj` 的 PBXFileReference、PBXBuildFile、Views/Settings group、主 target Sources。主源码不是全目录自动收集。

- MVP 不需要深链；若增加 `minis://settings/auto-compaction`，需同时扩展 SettingsDestination、其 destination 映射和 DeepLinkCoordinator 的 settings 解析，不能只加 enum case。旧聊天确认弹窗启用动作也必须保持同源。

## 5. 最容易破坏的 invariants

### 工具调用配对

1. tool_result 是 user-role，不代表真实用户回合；截断不能发生在 assistant(tool_use) / user(tool_result) 中间。
2. 对 Responses 组合 id（`call_id|fc_id`），沿用 `pairingKey` 的 call_id 归一化，不能直接比较整个字符串导致假孤儿。
3. `dropOrphanedToolParts` 会丢没有 use 的 result，并为历史上无 result 的 use 合成 interrupted error；**最后 assistant 的 tool_use 豁免**，因为可能正处于发起工具与结果加入之间。不能在这里用自动压缩把仍将执行的工具提前判失败。
4. pre-anchor 裁剪/重放已会裁掉大型结果及配对的 use，摘要拼接之后仍须走现成 `effectiveAgentHistory()` 修复出口；不要直接把 uncounted 结果拿去 provider。
5. image trim/offload 是已有优化，`src/ios/Agent/Chat/AIChatViewModel+Offloading.swift/offloadContextIfNeeded` 会原地改写内存 history 中重载荷为文件 stub，但不等同于删除原聊天。新预算无需扩张该行为，尤其不能改写未完成 file_write/file_edit 参数。

### 当前回合、取消与队列

1. 非循环压缩必须 `startCompactTask`，Stop 才能取消；循环内压缩留在原 currentTask 中 await，不能用 schedulePostCompactDrain 再启动第二条 loop。
2. 保留 `compactBefore` 进入时 isProcessing 的恢复语义；in-loop 若被重置为 false，会允许 DB reload 与 streaming bubble 脱离。
3. 复用 guard 的压缩后 fresh assistant bubble，重置 msgIdx/runMsgId/committedBlockCount，否则新内容追加在 divider 上方灰色旧泡泡。
4. 管理空间的 continue 需要 `turnCount -= 1` 抵消 defer，但**不能重置**整个 maxAgentTurns，防止无限任务。
5. await 摘要期间可能删除聊天、重载/换模型；用 raw id 复验、已有索引夹紧及 cancellation 检查，不跨 await 依赖旧数组下标。未能落库的 anchor 不写 marker。

### usage、预算与安全

1. 使用 `contextMeasurement().measured = ratio × (effective outbound history + fixed system/tools)`；不用 sessionInputTokens 累计数、最后 bubble usage 或 raw agentHistory 全量大小。
2. 不恢复 `max(estimate, lastAPIReport)`：旧 usage 描述压缩前请求，会使摘要后持续假超窗、连续压缩并停机。
3. 保留 `recordContextDispatch` 与相同请求 usage 的配对，模型回退按真正 served model 校准；新预算不得修改 lastDispatchWindow，使服务端 overflow 错误错误地归因到预算。
4. 第一轮尚未构造实际 prompt 时先 ensureContextFixedTokens；in-loop 在 offload 后再测软线；压缩成功调用 announceContextUsageAfterCompaction，避免 UI 还显示压缩前百分比。
5. 使用 resolved 当前 entry，不使用 selectedModel、旧 group resolvedEntryId 镜像或全 group 最小窗口；需求是预算与**实际所用模型 + 绑定 group cap**的最小值，不是所有候选模型中的最小值。真正 fallback 后重算即可。
6. 软失败应只阻止同类无意义重试，不可抑制稍后增长到真实安全线时的压缩机会。
