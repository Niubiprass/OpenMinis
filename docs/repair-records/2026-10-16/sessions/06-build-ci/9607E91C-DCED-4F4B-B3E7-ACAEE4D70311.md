### 1. [P1] 软预算压缩无收益时直接发送，绕过压缩后的真实窗口安全复验

**位置：** `AIChatViewModel.swift:6391–6417`。

`checkContextBeforeSend` 在 `await compactBefore(...)` **之前**判定为 `.ok`；软预算路径压缩后仅检查 `sizeAfter >= sizeBefore`，无收益时便 `break` 出 switch，直接进入同轮 API dispatch，不再执行 `settleWithoutCompacting()` 或重新检查 safety verdict。

“无收益”不能推出“请求仍安全”：成功摘要可能比原内容更大，压缩模型 fallback 也可能改变有效窗口/标定。`compactBefore` 没有“仅提交缩小请求的摘要”保障。

**分支反例：**
- 真实窗口 64,000，原请求 53,000，低于该档 54,000 compact 线，safety 为 `.ok`。
- 软预算 50,000，其触发线为 42,500，因此进入预算压缩。
- 压缩后请求增至 65,000。
- 当前分支设置 no-progress 后直接发送，跳过真实窗口处理。

该反例已用纯 Python 决策模型核对，**不是实机复现**。

**建议：** 无收益只应禁止后续软预算重试；发送前仍必须基于压缩后的当前模型/窗口执行原有 safety/settle 决策。软目标未达标本身不得报 Context Full，但新的真实窗口不够时必须恢复安全路径。补充“摘要增长”“压缩期间切换较小窗口”测试。

### 2. [P2] 宿主 rootView 的固定宽度上限不会随布局宽度扩张更新

**位置：** `iOS15Compat.swift:442–458, 503–507, 529–531`；关联 `MessageListInfrastructure.swift:1335–1350`。

`apply` 把当时 `resolvedHostingWidth(bounds.width)` 的结果作为常量写入根 `.frame(maxWidth: ...)`。之后 fitting 入口虽然使用新的布局宽度，却不更新这个 root frame cap。宽度变化的 prewarm 仅清尺寸缓存、重排附件并 invalidate layout，不刷新 configuration/rootView。

此外，若 reconfigure 在 cell bounds 更新之前发生，`min(旧 bounds, 新 collection width)` 仍会把旧窄宽写回。

**静态反例：** 旧 cell 宽 390，新 collection 宽 744；apply 得到 root cap 390，随后 fitting 使用 744，但 SwiftUI 根仍受 390 限制。这会造成窄列→宽列、旋转等场景的测量宽度与实际根布局不一致，不能依赖下一个 token 自愈。

**建议：** 宿主根上限须跟随真正当前 collection/layout 宽度同步，避免旧 cell bounds 覆盖已知的新宽度；宽度变化时刷新根约束/根视图，并保持相同 MessageListItem 身份。验证 `390→744→390`、侧栏展开/收起，不依赖下一次流式更新。

## 可后续

### 3. [P2] 软预算参与暖机裁剪，但已有 marker 缓存不随偏好变化更新

**位置：**
- `AIChatViewModel+Compaction.swift:275–285`
- `AIChatViewModel+Persistence.swift:2146–2155`
- `AIChatViewModel.swift:1247–1254`

`trimWarmUpToFit` 新增读取全局软预算，但 `warmUpDropByMarker` 仍仅按 marker ID 缓存 drop 数；已有缓存会直接绕过新预算计算。当前仓库内未找到启用/禁用 auto、调整预算时使其失效的路径。

结果：
- 降低预算后，旧暖机保留策略可能导致额外压缩。
- 提高预算或关闭 auto 后，已裁掉的可选暖机不会恢复，直到新 marker/新 VM。

这不绕过硬窗口 safety，因此列为后续项。

**建议：** 缓存键加入 enabled/normalized budget 快照，或仅在偏好变化时重新决定。继续保持“同一偏好下每 marker 固定一次”，不要退化成逐 token 滑动裁剪。

## 指定疑点的审查结论

以下不计为 findings：

- **`.id` optional 根类型：当前正确。** fast path 虽用解包后的 `identity` 判等，但实际根表达式调用 `.id(newConfig.contentIdentity)`，类型仍为 `AnyHashable?`；重建路径 `.id(identity)` 的局部变量同样为 `AnyHashable?`。未发现 optional/nonoptional 导致根泛型类型不一致。
- **visibility / availability：未发现确定新增错误。** `contentIdentity` 的 fileprivate 访问均在同文件内；桥接方法为 internal generic；internal `MessageListItem` 没有泄露到 public API。新增调用未见要求 iOS 16 的 API。
- **身份与复用：** 四处均传完整 `MessageListItem`；block 身份含 message UUID、block UUID。相同身份仍重新赋 rootView，不同身份销毁旧 host 并清测量兜底。没有发现本次变更必然复用旧文本/旧模型的证据。测量高度缓存重置不等于 renderer cache 被清空。
- **尾沿 reflow：未发现确定丢最终更新。** 新高度在调度合并前已写入缓存；合并时仍保留已安排任务，任务执行时读取当前缓存并 invalidate；时间戳已从 static 改为实例状态。最后 token 的源码模型测试通过，但 tracking/deceleration 仍需实机验证。
- **淡入生命周期：** 完整替换前取消旧范围、iOS 15 禁止新动画、dismantle/前后台清理均有路径，未发现确定新增编译或生命周期错误。14 项源码测试不能替代设备回归。
- **策略边界需产品确认：** 新软预算不检查 `manualCompactAllowed/exhaustedOnly`，开启全局 auto 后可在旧小窗口 tier 的 `.ok` 区间主动压缩。若全局 opt-in 明确覆盖旧 tier 限制，这是设计；否则应补 gate。缺少该约定，未将其作为确定 finding。
