# OpenMinis 唯一编译、发布与应用更新入口

## 固定不变

- 仓库：`Niubiprass/OpenMinis`，只涉及这个 App，不涉及插件仓库。
- 正式分支：`ios15-160652-four-features`。不要按歌词、桌宠或 build 号再开正式通道。
- 编译发布：`.github/workflows/openminis-app.yml`。本次只迁移一次以彻底停用可重跑危险旧代码；之后文件路径与名字固定，不按功能或build另开入口。新ID要推送后核实，不假称已注册。
- 手机更新：`beta-latest/latest.json`，App 的现有地址不改。
- 当前市场版本 `1.16`、CFBundleVersion `160652` 保持；仅 `scripts/app-release.json` 的 `build` 递增。
- 此本地候选预留下一个编号386，未发布、未构建。失败385的记录保留，不伪装为成功版。

## 每次获准发布

1. 功能改动合入同一正式分支，完成本地检查。只在版本配置里递增build、更新说明，不再改工作流的分支过滤/包名。
2. 单独获得推送/CI/发布授权。固定流程在GitHub编译，不在iSH编iOS。
3. 先验证build高于线上，再完整执行原有源码/原生检查、Xcode编译、签名/权限、终包CRC、代码页/篡改负例。
4. 同一次CI上传已验IPA、暂存新清单，校对SHA256与大小，保留旧包/清单后才切`latest.json`；发布任务全局串行且不自动取消。
5. 手机同款匿名清单GET和IPA HEAD成功、清单逐字匹配后才记`PUBLISHED_PUBLIC_FEED_VERIFIED`。只生成artifact不算发布完成。
6. 之后用户在App里点应用更新。助手不代安装，不擅自注销/重启；插件仍单独DEB安装。

## 故障与边界

- 编译/验包失败不会运行发布步骤，线上上一版不动。
- 上传IPA/暂存清单失败不会动线上清单。首次改名之前先把不可变事务记录存进同一Release（绑定source commit、旧清单原字节/资产ID、新包大小SHA及ready ID）；直到公开验证结束的全部阶段，失败或可捕获取消都尝试恢复这个事务的旧清单，而不是覆盖别的更新。
- SIGTERM/SIGINT有回退处理；进程被强杀、网络全断不能保证当场恢复。下一次获准执行同一入口时，可按已核对的事务恢复缺失latest，再复用**同source/同build/同SHA**的原包补验，绝不随便选一个历史版本，也不重新编同号新包。
- GitHub不提供原子交换两个asset名称的API，改名之间仍有短暂空档；网络始终不可用时仍需人工恢复。不能把离线模拟或重试逻辑当成GitHub真实成功。
- 旧编号不能覆盖新编号；同号只能指向完全相同的来源、元数据和包。完整工作流重试由prepare选`APP_MODE=resume`，跳过Xcode/签名/上传；这不是放宽新构建严格递增规则。
- 固定release与tag不删、不重建；旧包保留回退。所有动作受当前授权约束。
- 旧App功能问题不在此次流程整理中修复：歌词显示、真实音乐跟拍尚未真机验收；预编译VAD minOS15.6旧例外保留；385的fresh-PID原生fixture失败未修改/放宽。

## 历史入口

5个本地旧编译YAML（包括原正式入口）逐字归档到`.github/archived-workflows/*.disabled`。
上游版本监听仍只发提醒和提交监听状态，不编译、不发布；保留这项旧辅助功能，不算第二个编译或更新通道。

GitHub服务器还登记着历史编译ID。待单独批准推送后，还须停用全部8个旧编译ID（见归档README），包括旧正式ID384811054；保留全部历史日志、分支、Release和回退IPA。现在未调用停用API。停用不会自动取消正在运行的旧任务，迁移前须查活动run。

默认分支main仍为旧上游锚点，缺少新正式workflow。本地整理未修改它或仓库默认设置。正式分支push可以自动触发新流程，但GitHub网页手动按钮要在另获批准后把仓库默认分支切到同一正式分支（或另行同步workflow到main，二选一，不偷偷代做）。旧main、全部历史分支不删；不要从历史run点rerun来发新版本。
